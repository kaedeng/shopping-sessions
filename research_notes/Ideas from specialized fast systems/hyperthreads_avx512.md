# Hyperthreads and AVX-512 on Intel server cores: tuning rules for a table-driven SIMD parse loop and short vector passes

Reading notes. "Measured" means the source reports its own measurement; "documented" means a vendor statement; anything about our program is under Inferences. Abbreviations: SKX = Skylake-SP/X, CLX = Cascade Lake, ICX = Ice Lake-SP (Sunny Cove), ICL = Ice Lake client, SPR = Sapphire Rapids (Golden Cove), EMR = Emerald Rapids, GNR = Granite Rapids, ADL-P = Alder Lake P core (Golden Cove, stands in for SPR in uops.info). Sources marked "(search summary)" were seen only as a search-result summary, not read in full. Three PDFs (Agner Fog's manual, an Intel optimization manual, Intel's Hot Chips 32 deck) were read as extracted text.

## 1. Hyperthreading: what two siblings share, what a pair yields, and which code properties move it

### Takeaway
On Intel cores the reorder buffer, load buffer and store buffer are split in half per thread while the scheduler, execution ports, caches, fill buffers and data TLBs are fought over, so a loop that already saturates one port class (port 5 for shuffles, the single store port on SKX/CLX) gains nothing from its sibling. No source measures the pair yield of 256/512-bit integer code directly; the nearest measurement (Cloudflare, 512-bit ChaCha20-Poly1305 on Skylake-SP) shows per-core throughput with both siblings at about half of one thread's.

### Cited Findings
**Sharing policy (Intel)**
- Documented (Nehalem description, kept in later manuals): replicated per thread: register state, return stack buffer, large-page ITLB. Statically partitioned: "load buffers, store buffers, re-order buffers, small-page ITLB are statically allocated between two logical processors". Competitively shared: "the reservation station, cache hierarchy, fill buffers, both DTLB0 and STLB". Front end alternates between the threads. Execution units are "HT unaware". — [Intel Optimization Reference Manual 248966-025, section 2.3](https://www.cs.princeton.edu/courses/archive/fall13/cos217/reading/ia32opt.pdf)
- Measured on Skylake: running code on the sibling halves the usable store buffer even if the sibling does no stores; the partition applies only while both threads are active; the store buffer has 56 entries (55 measured). — [Fallout paper](https://arxiv.org/pdf/1905.12701)
- Measured: line fill buffers are 10 entries before Skylake and 12 on Skylake and newer (Intel documents 10); Intel calls them competitively shared; when both siblings store, latency rises for both. — [ZombieLoad paper](https://arxiv.org/pdf/1905.05726)
- Conflict: Agner Fog lists the reorder buffer and the read/write buffers as "shared competitively" for Sandy Bridge and says later cores share "in the same way". Intel's manual and the Fallout measurement say the buffers are statically split. — [Agner Fog, microarchitecture manual, sections 9.15, 11.14, 12.14](https://www.agner.org/optimize/microarchitecture.pdf)
- Documented (Intel, Hot Chips 32): the allocation queue is 64 entries per thread on Skylake and "70/thread; 140/1 thread" on Sunny Cove, so the queue in front of rename is per-thread. — [Hot Chips 32 Ice Lake-SP deck](https://www.hc32.hotchips.org/assets/program/conference/day1/HotChips2020_Server_Processors_Intel_Irma_ICX-CPU-final3.pdf)

**Structure sizes (whole core, before any split)**
- Skylake/CLX against Sunny Cove/ICX (Intel's own table): in-flight loads + stores 72 + 56 against 128 + 72; scheduler 97 against 160; integer + vector register files 180 + 168 against 280 + 224; L1D 32 KB against 48 KB; L2 TLB 1.5K against 2K; L2 1 MB against 1.25 MB; L1D bandwidth 128 B load + 64 B store per cycle on both; ICX adds "second FMA" on the server core. — [Hot Chips 32 Ice Lake-SP deck](https://www.hc32.hotchips.org/assets/program/conference/day1/HotChips2020_Server_Processors_Intel_Irma_ICX-CPU-final3.pdf)
- Reorder buffer: Skylake 224, Ice Lake 352; Zen 3 256, store buffer 64. — [Travis Downs, "Performance speed limits"](https://travisdowns.github.io/blog/2019/06/11/speed-limits.html)
- Golden Cove P core: micro-op cache 4,096 µops, L1D 48 KB 12-way, L2 1,280 KB on client. SPR server: L2 2 MB with 16-cycle latency; two 512-bit loads per cycle from L1; mask register file about 152 entries; only a subset of vector registers is 512-bit capable. — [Agner Fog, chapter 13](https://www.agner.org/optimize/microarchitecture.pdf); [Chips and Cheese, "A peek at Sapphire Rapids"](https://chipsandcheese.com/p/a-peek-at-sapphire-rapids)
- Micro-op cache on Sandy Bridge through Skylake/CLX: 32 sets x 8 ways x 6 µops = 1,536 µops; at most 3 ways (18 µops) per aligned 32-byte block of code; a block that does not fit is decoded by the legacy decoders and the switch costs. Agner: the µop cache serves "loops up to approximately 1000 instructions"; Ice Lake's is 50% larger and he advises keeping hot spots under 2,000 instructions. — [Intel manual, 2.1.2.2](https://www.cs.princeton.edu/courses/archive/fall13/cos217/reading/ia32opt.pdf); [Agner Fog, 10.3, 11.3, 12.15](https://www.agner.org/optimize/microarchitecture.pdf)

**What a pair yields**
- Agner (Skylake and Ice Lake chapters): "If the code aims at more than two instructions per clock cycle, then there is no advantage in running two threads in each core"; a pair helps when time goes to cache misses and branch mispredictions; if a shared resource is the bottleneck each thread "is likely to run at less than half the single-thread speed". Each thread gets half the pipeline's throughput. — [Agner Fog, 9.15, 11.14, 12.14](https://www.agner.org/optimize/microarchitecture.pdf)
- Measured, Skylake-SP (2 x Xeon Silver 4116, 24 cores, 48 threads, one 512-bit FMA unit): OpenSSL AVX-512 ChaCha20-Poly1305 gives 2.89 GB/s on one thread and "just over 35 GB/s" on all 48 threads, 1.46 GB/s per core, "roughly 50%" of one thread; AES-GCM (no 512-bit) keeps about 80%. Clock drop and sibling contention are not separated. — [Cloudflare](https://blog.cloudflare.com/on-the-dangers-of-intels-frequency-scaling/)
- Ice Lake-SP against Cascade Lake, SPEC CPU: +16.3% and +10.4% per thread with one thread per core, but +8.2% and +7.4% with both siblings; Intel's explanation is that the better core leaves less for the sibling. — [AnandTech Ice Lake-SP review, page 8](https://at-web1.www.anandtech.com/show/16594/intel-3rd-gen-xeon-scalable-review/8) (search summary)
- Anecdotes for vector-heavy encoders: x264 17% faster with hyperthreading on, x265 about 8% (Raptor Lake, forum posts, uncontrolled). — [AnandTech forum thread](https://forums.anandtech.com/threads/on-the-virtues-of-smt-or-lack-thereof.2609570/post-40921558) (search summary)

**Port and memory limits that both siblings draw on**
- Skylake/SKX: 4 fused µops per cycle, 2 loads and 1 store per cycle; a store with an indexed address cannot use port 7, so its address µop takes a load port. Ice Lake: 5 µops, 2 loads, 2 stores per cycle but two stores only if consecutive stores hit the same cache line. A load that crosses a 64-byte line counts as two. Shuffles use only port 5; vector ALU has three ports, "or two for AVX-512". One taken branch per 2 cycles except tiny loops. — [Travis Downs, "Performance speed limits"](https://travisdowns.github.io/blog/2019/06/11/speed-limits.html)
- Intel rule for code running on two logical processors: block for one quarter to one half of the target cache; reduce the number of writes in the inner loop; do not write more than four distinct cache lines' streams per inner loop (rule 59 dates from the Pentium 4's write-combining buffers). — [Intel manual, 3.6.10, 8.5.5, 8.6.1](https://www.cs.princeton.edu/courses/archive/fall13/cos217/reading/ia32opt.pdf)

### Inferences
- Per-thread window with both siblings busy (halving the documented sizes): SKX/CLX 112 reorder-buffer entries, 36 loads, 28 stores; ICX 176, 64, 36. One event line of ours is about 200 instructions (positional.md), so on CLX a thread's window holds about half a line and on ICX about one. Line-to-line overlap, which is free on Zen 4 alone (320 entries), mostly disappears on a CLX pair; what counts there is the critical path inside one line and the µop count per port.
- Rule for a port-bound loop: the pair's combined rate is ports of the scarcest class divided by µops of that class per line, the same bound as one thread alone. Shortening dependency chains or front-end work helps one thread and not the pair; removing µops from the scarcest port helps both by the same factor. Our 3% gain from breaking the line chain and the exact 2.0x under a sibling both say the fused parse is in this regime on Zen 4. The number to drive down per generation is µops per line on: port 5 (SKX/CLX, all shuffles and mask compares), port 4 (the one store port on SKX/CLX), ports 2/3 (loads, and indexed store addresses on SKX/CLX), port 1 (`tzcnt`, `pdep`, `pext`, scalar multiply).
- Stores per line matter twice on SKX/CLX: one store per cycle for the whole core, and 28 store-buffer entries per thread. At 5 stores a line plus the decode's roughly 5 spills a line, a pair of siblings uses about a sixth of the store port at 120 cycles a line; at 17 + 5 it was over a third. Stores to a base register plus displacement let the address µop use port 7 and leave both load ports for the table rows.
- Read-only tables are held once for both siblings (same physical lines), per-thread buffers twice. Budget a thread about 8 to 16 KB of private L1D on SKX/CLX and 12 to 24 KB on ICX/SPR, using Intel's quarter-to-half rule.
- The hot parse (per-line loop, 640-instruction decode, scatter) is on the order of 900 instructions of long EVEX encodings. A 1,536-µop cache with at most 18 µops per 32-byte block is shared by two threads running it; Agner's "about 1000 instructions" limit is for one thread. On SKX/CLX a pair may fall partly back to the legacy decoders, which the two threads use in alternation. Zen 4's 6,912-µop cache, whose entries two threads running the same code share (section 2), cannot show this.

### Gaps
- No source gives a measured pair-over-single speed-up for scalar, 256-bit and 512-bit integer loops on SKX/CLX, ICX or SPR. The Cloudflare figure mixes the clock drop in.
- Whether the Intel micro-op cache is split per thread or shared when hyperthreading is active was not confirmed from a primary source for any of the three generations; nor was the sharing of the physical vector register file.
- Golden Cove's reorder buffer, load and store buffer sizes and fill buffer count: the page that lists them returned 404; the widely quoted 512-entry reorder buffer is not sourced here.
- Intel's current manual (volume 1, 2024 or later) returned 403; the sharing list above is from the 2011 edition.

## 2. Zen 4 against the Intel cores: which of our findings will not transfer

### Takeaway
Zen 4 runs a 512-bit instruction as one µop on two 256-bit pipes, has two shuffle pipes, cheap `tzcnt`, one-µop `vpmullq` and no clock penalty; Intel has a real 512-bit datapath but only port 5 for every shuffle and mask compare, three µops and 15 cycles for `vpmullq`, and a 512-bit mode that takes port 1's vector unit away. Timing on the 7800X3D therefore understates what 512-bit registers buy on Intel and overstates what shuffles, `vpmullq` and `tzcnt` cost nothing there.

### Cited Findings
**Zen 4 core**
- 512-bit instructions are "executed with a single µop using two 256-bit pipes simultaneously"; six vector pipes (two multiply, two add, two memory); 256-bit simple integer ops 4 per cycle, 512-bit 2 per cycle; one 512-bit read per cycle, one 512-bit write per two cycles; mask compares have latency 3, 4, 5 for 128, 256, 512 bits against 1 for AVX2 compares; µop cache 6,912 µops; reorder buffer 320; 192 vector registers. — [Agner Fog, chapter 24](https://www.agner.org/optimize/microarchitecture.pdf)
- "The µop cache is shared between threads... If two threads are running the same code in the same core, they can both use the same entries in the µop cache, but they only get a throughput of 3 µops per clock each." Fetch is 16 bytes per cycle alone and 8 to 10 per thread with two threads. — [Agner Fog, 24.2, 24.5](https://www.agner.org/optimize/microarchitecture.pdf)
- Store forwarding on Zen 4: write then read costs 8 cycles (general registers) or 9 (vector); a read larger than or partly overlapping the write costs about 11 cycles more. Zen 4 can also "mirror" some memory operands so a reload has no latency. Skylake: 4 to 5 cycles, about 11 extra for a read bigger than the write, 4 to 5 extra across a cache line. — [Agner Fog, 24.17, 24.18, 11.13](https://www.agner.org/optimize/microarchitecture.pdf)
- A 512-bit store is two µops and two store-queue entries; the store queue did not grow from Zen 3 (64) and is "much smaller than Intel's"; mask register file about 52 renames against about 144 on Sunny Cove and SPR. — [Chips and Cheese, Zen 4 part 1](https://chipsandcheese.com/p/amds-zen-4-part-1-frontend-and-execution-engine); [Chips and Cheese, SPR](https://chipsandcheese.com/p/a-peek-at-sapphire-rapids)
- AMD's sharing policy: retire queue, store queue and micro-op queue statically partitioned; other structures competitively shared, with watermarks in later generations. — [Chips and Cheese, interview with Mike Clark](https://chipsandcheese.com/2024/07/15/a-video-interview-with-mike-clark-chief-architect-of-zen-at-amd/) (search summary); [AMD EPYC SMT technology brief](https://www.amd.com/content/dam/amd/en/documents/epyc-business-docs/white-papers/amd-epyc-smt-technology-brief.pdf) (search summary)

**Intel 512-bit execution**
- SKX: the 256-bit units of ports 0 and 1 combine into one 512-bit unit reached through port 0, "while port 1 can be used for other purposes"; a second 512-bit unit sits on port 5; integer vector adds are 3 per cycle at 256 bits and 2 per cycle at 512; permutes that cross 128-bit lanes "are always handled by port 5". Ice Lake: the same, with port 5 alone 512 bits wide; 512-bit stores one per cycle using ports 4 and 9 together. — [Agner Fog, chapters 11 and 12, execution units](https://www.agner.org/optimize/microarchitecture.pdf)
- SPR: ports 0 and 1 run as two 256-bit units or one 512-bit unit "depending on whether 512-bit FMA instructions are in the scheduler"; mixing 256-bit and 512-bit instructions does not exceed the 512-bit rate. — [Chips and Cheese, SPR](https://chipsandcheese.com/p/a-peek-at-sapphire-rapids)

### Inferences
- "2.0x slower with a sibling" will not be better on SKX/CLX for the same code and is likely worse in cycles per line: every shuffle and every compare-into-mask of the per-line loop queues on one port there (two pipes on Zen 4), so the loop is port-bound with one thread already. On ICX/SPR a 256-bit `vpshufb` can also use port 1, but not while 512-bit µops are in the scheduler, and the scheduler is shared: a sibling in its 512-bit step plausibly takes port 1's vector unit from this thread's 256-bit work too (the sharing across siblings is our inference, not sourced).
- Dearer on Intel than our Zen 4 timings suggest: (1) `vpmullq`, three µops and 15 cycles, so the decode's 27 multiplies per 8 rows are 81 µops on ports 0 and 5 if they are `vpmullq`; where a factor and the value fit 32 bits use `vpmuludq` (one µop, 5 cycles). (2) Every `vpshufb`/`vpermd`/`vpermb`, `vpcompress` and EVEX compare-into-mask: port 5 only. (3) `tzcnt`: one port and 3 cycles against four ports and 1 cycle. (4) Multiply-add latency 5 against 3. (5) Spills and reloads: 4 to 5 cycle forwarding with no memory mirroring, a halved store buffer, one store port on SKX/CLX; the decode's 40 spills and 60 constant reloads per 8 rows cost more there.
- Cheaper on Intel: `vpcompressd`/`q` to memory (4 µops against 144 on Zen 4), so a compressing store may be worth re-measuring on Intel even though it was rightly dropped here; `vpermb`/`vpermd` latency (3 against 4 to 5); 512-bit loads and stores at full width; mask compares (3 to 4 cycles against 5).
- 512-bit registers pay more on Intel than on Zen 4: one zmm shuffle does 512 bits on port 5 where a ymm shuffle does 256 on the same port (SKX/CLX), and non-shuffle work gets 2 x 512 bits per cycle against 3 x 256. An idea that Zen 4 cannot validate by timing: run the per-line shuffle and multiply-add work for two lines in one zmm (`vpshufb` and the multiply-adds are per 128-bit lane), filling the upper half with a memory-source insert. It halves port 5 µops per line on SKX/CLX and keeps the core in one width mode. Judge it with a port simulator for CLX and ICL, not with the 7800X3D.
- Making the masks alone took 36 ms with AVX-512 compares against 55 ms with AVX2 on Zen 4 (our notes), but on Intel each compare into a mask register is a port 5 µop plus a port 0 `kmov`, in direct competition with the shuffles; AVX2 `vpcmpeqb` + `vpmovmskb` should run on ports 0 and 1 (from memory, not looked up). Which is better on Intel depends on port 5 occupancy and is a simulator question.

### Gaps
- Mysticial's "Zen4's AVX512 Teardown" could not be fetched (403/404); its detailed latency tables and its statement about the absence of throttling on Zen 4 are not quoted here. A forum copy confirms only his summary: no power or thermal issues, "stellar shuffle support". — [forum copy](https://discussion.fool.com/t/zen4s-avx512-teardown/76016)
- uops.info has no Sapphire Rapids or Ice Lake-SP rows in the pages read; server port 5 behaviour for multiplies is taken from the SKX rows and the vendor statements.
- No source says whether one sibling's 512-bit µops fuse ports 0 and 1 for the other sibling's 256-bit µops.

## 3. AVX-512 frequency licences and port availability by generation

### Takeaway
On SKX/CLX any 512-bit instruction, and sustained 256-bit multiplies, put the core (both siblings) at the middle licence within about 20 µs and keep it there about 0.65 to 2 ms after the last one; only dense 512-bit multiplies or floating point reach the lowest. ICX keeps three levels with much smaller drops and no halt; SPR and EMR show no fixed 512-bit offset in measurements (EMR: 2.95 against 3.01 GHz). 256-bit multiplies are not licence-free on SKX/CLX/ICX: they are the same class as light 512-bit code.

### Cited Findings
**Skylake-SP, Cascade Lake**
- Measured (Xeon W-2104, SKX, no turbo): L0 3.2 GHz, L1 2.8, L2 2.4. A single `vpor zmm` requests L1: about 9 µs at full clock but with dispatch throttled about 4x (scalar code nearby is slowed too), then a halt of about 11 µs, then 2.8 GHz; the return to 3.2 GHz comes no sooner than about 650 to 680 µs after the last wide instruction, with another halt of about 11 µs. `vpor ymm` causes the same 4x throttled period (voltage only) and no frequency change; xmm causes nothing. Packed as tightly as possible (period 760 µs) the halts cost under 3%; the clock loss is 12.5%. Once a 512-bit register has been written, later SIMD instructions count as 512-bit until `vzeroupper`. Heavy-instruction density thresholds were not tested. — [Travis Downs, "Gathering Intel on Intel AVX-512 Transitions"](https://travisdowns.github.io/blog/2020/01/17/avxfreq1.html)
- Xeon Gold 5120 (Skylake-SP) turbo table: normal 3.2 GHz with 1 active core and 2.7 with 9 to 12; "AVX2" row 3.1 and 2.3; "AVX-512" row 2.9 and 1.6. The rows mean licences: the AVX-512 row needs sustained heavy 512-bit use, "approximately one such instruction every cycle"; the AVX2 row covers all other 512-bit use and sustained heavy 256-bit. Heavy means floating point and integer multiplication; shuffles and logic are light. Early heavy instructions run "say 4x slower" until the licence is granted. Downclocking is per core and lasts about 2 ms. Light 512-bit on all cores costs about 15% of clock on this part. — [Daniel Lemire](https://lemire.me/blog/2018/09/07/avx-512-when-and-how-to-use-these-new-instructions/)
- Measured (2 x Xeon Silver 4116, Skylake-SP): with all TLS traffic on AES-GCM the cores sampled at 2.40 GHz, with AVX-512 ChaCha20-Poly1305 at 2.18 GHz (9% lower); nginx served 10% fewer requests although the 512-bit code was 2.5% of CPU time; with 10% of requests on it the loss was 5.5%. Base 2.1 GHz, 1.8 with one core on AVX-512, 1.4 with all. — [Cloudflare](https://blog.cloudflare.com/on-the-dangers-of-intels-frequency-scaling/)
- Measured (Skylake-X at 4 GHz): the upper halves of the vector units are powered off when idle; 256-bit code runs about 4.5x slower for about 56,000 cycles (14 µs) after first use and the units switch off again 2.7 million cycles (675 µs) after the last use; "similar times apply to 512-bit vectors". Ice Lake: about 50,000 cycles. — [Agner Fog, chapters 11 and 12, warm-up period](https://www.agner.org/optimize/microarchitecture.pdf)
- Cascade Lake retail parts "drop to lower frequencies (~600 to 900 MHz)" in AVX, AVX2 and AVX-512 workloads; we read the figure as the size of the drop. — [Tom's Hardware, Cascade Lake review](https://www.tomshardware.com/reviews/intel-cascade-lake-xeon-platinum-8280-8268-gold-6230-amd-epyc,6058-2.html) (search summary)

**Ice Lake-SP**
- Documented (Intel): three power levels remain. Level 0: SSE and light 256-bit. Level 1: heavy 256-bit ("FP Mul, INT Mul, VNNI, FMA 256b") and light 512-bit ("VPCLMUL, VAES, VBMI, Ld, St 512b"). Level 2: heavy 512-bit ("FP Mul, INT Mul, VNNI, FMA, VPMADD52 512b"). Intel claims a "significantly better frequency profile over prior generation" against SKX and CLX (chart; values not legible in the extracted text, and the level-to-class mapping is read from the slide's layout and its chart groups "SSE/256L", "256H/512L", "512H"). The same slide: "512-bit loads, 512-bit stores, 256-bit FP, integer multiply" are examples of instructions that do not consume high power. Core frequency-transition block time: 12 µs on CLX, about 0 on ICX. — [Hot Chips 32 Ice Lake-SP deck](https://www.hc32.hotchips.org/assets/program/conference/day1/HotChips2020_Server_Processors_Intel_Irma_ICX-CPU-final3.pdf)
- Intel describes the loss on 3rd-generation Xeons as 0 to 2 frequency bins. — [Intel cryptography paper, May 2021](https://intel.com/content/dam/www/central-libraries/us/en/documents/cryptography-processing-with-3rd-gen-intel-xeon-scalable-processors-19-may-2021.pdf) (search summary; the file now redirects to a 404)
- Measured, Ice Lake client (i5-1035G4): only width matters; 512-bit costs 100 MHz with one active core (3.7 to 3.6 GHz) and nothing with 2 to 4 cores (3.6, 3.3, 3.3); heavy 512-bit costs no more than light; heavy 256-bit costs nothing. Rocket Lake i9-11900K: no licence-based downclocking. — [Travis Downs, "Ice Lake AVX-512 Downclocking"](https://travisdowns.github.io/blog/2020/08/19/icl-avx512-freq.html)

**Sapphire Rapids, Emerald Rapids**
- Measured (Xeon Platinum 8480 in a cloud instance): no fixed 512-bit offset; clocks "go all over the place" without a link to instruction mix; up to 3.8 GHz observed with 512-bit vectors. Google's SPR preview ran at a locked 3 GHz. — [Chips and Cheese, SPR](https://chipsandcheese.com/p/a-peek-at-sapphire-rapids)
- Measured (Xeon Platinum 8592+, EMR, 68 tests): peak all-core frequency 2.95 GHz with AVX-512 against 3.01 GHz without; Phoronix says SPR behaves alike. Embree on SPR: peak frequency "minimally impacted" by AVX-512. — [Phoronix, 5th Gen Xeon AVX-512](https://mail.phoronix.com/review/intel-5th-gen-xeon-avx512/5) (search summary); [Phoronix, Embree on SPR](https://www.phoronix.com/review/embree4-sapphire-rapids/3) (search summary)

**The second 512-bit multiplier on port 5**
- SKX: Platinum 81xx and Gold 61xx have two 512-bit FMA units, Gold 51xx (except 5122), Silver 41xx and Bronze 31xx one; CLX "depends upon CPU SKU"; all Ice Lake-SP SKUs have two; SPR has two "as on prior Intel server CPUs". Skylake-X desktop parts under ten cores lack it. — [Colfax Research](https://colfaxresearch.com/xeon-2017/) (search summary); [Microway, Ice Lake-SP](https://www.microway.com/knowledge-center-articles/detailed-specifications-of-the-ice-lake-sp-intel-xeon-processor-scalable-family-cpus/) (search summary); [Chips and Cheese, SPR](https://chipsandcheese.com/p/a-peek-at-sapphire-rapids); [Agner Fog, chapter 11](https://www.agner.org/optimize/microarchitecture.pdf)
- What its absence changes (uops.info, client ICL and ADL-P lack it): 512-bit `vpmullq` one per 3.0 cycles instead of 1.5, `vpmuludq` one per cycle instead of two; `vpaddd` zmm (p05), `vpternlogd` (p05) and all shuffles (p5) are unchanged because port 5's 512-bit integer unit exists on every part. — [vpmullq](https://uops.info/html-instr/VPMULLQ_ZMM_ZMM_ZMM.html); [vpmuludq](https://uops.info/html-instr/VPMULUDQ_ZMM_ZMM_ZMM.html)

### Inferences
- For a 0.3 to 1 s run the transitions themselves are noise (about 30 µs per core per change on SKX/CLX, none on ICX). What costs is the steady clock of the licence and, in stages that use wide registers only now and then, staying at the lower clock for 0.65 to 2 ms after each use: Cloudflare lost 10% with 2.5% of time in 512-bit code. Keeping 512-bit registers out of the place and sessions stages is right for SKX/CLX; a stage should be either free of them or use them throughout.
- The parse is at level 1 on SKX/CLX/ICX whether or not the decode is 512-bit, if its 256-bit `vpmaddubsw`/`vpmaddwd` are dense enough to count as sustained "INT Mul 256b". Dropping the 512-bit decode would then not restore the top clock. Conversely, splitting the decode's 27 multiplies per 8 rows into 256-bit halves moves them from the level 2 class to the level 1 class the loop is in anyway; it helps only if 27 multiplies per roughly 1,000 cycles reach level 2 at all, which Lemire's "about one per cycle" rule says they do not. Travis Downs did not test the density rule, so this is unverified.
- The licence is per core, and our eight threads all run the same stage, so no sibling is an innocent victim during the parse. After the parse each core drifts back to L0 within a millisecond or two if the following stage is clean.
- The scorer's ratio to our paired time was 1.12 without 512-bit code and 1.15 to 1.19 with it (positional.md): a 3 to 6% difference. That fits ICX-or-later behaviour, or a CLX whose classic pipeline was already at level 1; it does not fit a full SKX/CLX L0-to-L1 step at all-core load (about 15% on the Gold 5120).
- In a shared cloud host the other cores of the socket are busy, so the all-core rows of a turbo table apply, not the 4-active-core rows.
- A stage of short vector bursts separated by more than about 675 µs of scalar code pays Agner's 14 µs warm-up at 4.5x slower each time on SKX/CLX; negligible unless bursts are a few tens of microseconds long.

### Gaps
- Per-SKU turbo tables by licence and active cores for the cloud parts (8124M, 8175M, 8259CL, 8275CL, 8272CL, 8370C, 8375C, 8473C, 8488C, 8573C) were not found; the wikichip pages that hold retail tables refused connections.
- No licence or frequency data found for Granite Rapids servers.
- Intel's level table for Sapphire Rapids was not found; only measurements.
- Whether `vpmaddubsw`/`vpmaddwd` count as "INT Mul" for the licence, and the density at which sustained heavy use is recognised, are not documented in anything read. The performance counters `core_power.lvl0/1/2_turbo_license` (named by Lemire) answer it on real hardware.

## 5. Speculation and microcode mitigations that change the cost of ordinary user code

### Takeaway
Three mitigations reach plain user loops: store bypass disable (loads wait for every earlier store address; forced on seccomp tasks by default only before Linux 5.16), the jump-erratum microcode on Skylake through Cascade Lake (jumps touching a 32-byte boundary are kept out of the µop cache, 0 to 3% typical, up to 10% in outliers), and the Downfall microcode (gathers only, Skylake through Ice Lake). Loads-first batching and jump alignment answer the first two at no cost elsewhere.

### Cited Findings
**Store bypass disable (SSBD) and STIBP**
- The seccomp pull for v5.16-rc1 changed the default of `spec_store_bypass_disable` and `spectre_v2_user` from "seccomp" to "prctl"; since 5.16 a seccomp filter no longer turns on SSBD or STIBP by itself, though an administrator can still select it. — [seccomp updates for v5.16-rc1](https://lkml.iu.edu/hypermail/linux/kernel/2111.0/00943.html); [Kees Cook, RFC](https://lore.kernel.org/bpf/202110041214.564BF23@keescook/T/)
- The same change was submitted as a stable update for Ubuntu 22.04's 5.15 kernel in October 2022 (the patch posting was seen; that it was applied was not checked). — [Ubuntu kernel-team, SRU for Jammy](https://lists.snapcraft.io/archives/kernel-team/2022-October/133708.html) (search summary)
- Docker's default seccomp profile switches the mitigation on under the old default, and Docker has no option to keep seccomp without it; one project measured about 30% overhead for its workload. — [Shadow simulator documentation](https://shadow.github.io/docs/guide/sidechannels.html) (search summary)
- Mechanism: with SSBD a load does not execute speculatively until the addresses of all older stores are known; Red Hat: it "essentially disables the Memory Disambiguation optimization". On Intel processors with Hyper-Threading and without enhanced IBRS, setting SSBD on one hyperthread "might impact the performance of a sibling hyperthread on the same core". — [Intel, Speculative Store Bypass advisory](https://www.intel.it/content/www/us/en/develop/articles/software-security-guidance/advisory-guidance/speculative-store-bypass.html) (search summary); [Red Hat](https://access.redhat.com/security/vulnerabilities/ssbd) (search summary)
- Cost as published: Intel 2 to 8% on SYSmark 2014 SE and SPEC integer rate (client parts); TechSpot measured 1 to 3%. — [Packt summary of Intel's statement](https://www.packtpub.com/en-lu/learning/tech-news/intels-spectre-variant-4-patch-impacts-cpu-performance) (search summary)

**Jump conditional code erratum**
- The microcode update "prevents the jump instructions that overlay or end on 32-byte boundary" from being cached in the decoded µop cache; it applies to conditional jumps, macro-fused compare-and-jump pairs, unconditional jumps, calls and returns. Measured on a Core i9-9900K with SPEC CPU 2017: 0 to 3% slower, up to 10% in outlier microbenchmarks; the compiler mitigation (pad so that no jump crosses or ends on a 32-byte boundary) makes it negligible for about 3% more code, 1.5% if applied only in loops. — [Microsoft C++ blog](https://devblogs.microsoft.com/cppblog/?p=25462)
- Scope: "Skylake through Cascade Lake"; Intel's paper gives 0 to 4% excluding outliers; a dual Cascade Lake Xeon Platinum server lost about 1% overall. — [Phoronix forum, JCC benchmarks](https://phoronix.com/forums/node/1138567) (search summary); [Intel white paper 341810](https://www.intel.com/content/dam/support/us/en/documents/processors/mitigations-jump-conditional-code-erratum.pdf) (search summary; the file now redirects to a 404)

**Gather Data Sampling (Downfall)**
- The microcode mitigation is on by default and can be locked; status in `/sys/devices/system/cpu/vulnerabilities/gather_data_sampling`; a guest may read "Unknown: Dependent on hypervisor status". — [Linux kernel documentation](https://docs.kernel.org/admin-guide/hw-vuln/gather_data_sampling.html)
- It slows AVX2/AVX-512 gather instructions in user code; affects Skylake through Rocket Lake/Ice Lake; measured on 2 x Xeon Platinum 8380 (ICX): about 6% in OpenVKL, up to 34% in OSPRay; 19 to 39% on a Tiger Lake laptop; Intel warned of up to 50%. — [Phoronix](https://phoronix.com/review/intel-downfall-benchmarks) (search summary); [Tom's Hardware](https://www.tomshardware.com/news/intel-downfall-mitigation-performance-drop-linux) (search summary)

**Store and load quirks that mitigations sharpen (Intel, measured)**
- Store forwarding is 3 cycles at best and 4 or 5 if the load's address is ready early; a load whose base register and full address fall in different 4 KB pages takes 9 to 10 cycles; a page walk is cancelled while the store buffer holds a store of unknown address (Skylake family and earlier); two loads issued in the same cycle that miss L1 on the same line take 19 cycles instead of 12. — [Travis Downs, Intel performance quirks](https://github.com/travisdowns/uarch-bench/wiki/Intel-Performance-Quirks)
- Loads and stores whose addresses differ by a multiple of 4 KB are falsely dependent on Skylake ("It is not possible to read and write simultaneously from addresses that are spaced by a multiple of 4 Kbytes"). — [Agner Fog, chapter 11, cache and memory access](https://www.agner.org/optimize/microarchitecture.pdf)

### Inferences
- The scorer's kernel decides SSBD: 5.16 or later leaves it off under Docker, and an updated Ubuntu 22.04 probably does; kernels before 5.16 without a backport (Amazon Linux 2 at 4.14 or 5.10, Debian 11 at 5.10, going by version alone) leave it on. Our Docker Desktop kernel has it on, so our timings already include it; if the scorer has it off, loops with late store addresses are faster there than here, never slower.
- Shape for a loop with disambiguation off: make every store's address available early and from induction variables, not from the data path (fixed staging slots, a cursor advanced by a count computed apart from the record's contents); in a batch, do all loads first and then all stores (measured at 3.5 to 1.6 ns a key in x86.md); keep the number of in-flight stores with data-dependent addresses small, because every later load, including the next line's two 64-byte loads and its table rows, waits for all of them. A page walk cancelled behind an unknown-address store (Skylake family) makes this worse when the staging area and lists span many pages: another reason for 2 MB pages there.
- Storing 16-byte records and reloading them as a wider vector is a forwarding failure (about 11 cycles on Skylake and Zen 4) on top of SSBD's wait; pass them in registers or reload with the same width and address.
- The jump erratum matters because we build for `cascadelake` and LLVM does not pad for it by default. The per-line loop's branches (one per window, the row-shape exits, the every-8-lines step) land on 32-byte boundaries at random; each one that does drops its 32-byte block to the legacy decoders, which two siblings share by alternation. LLVM has an assembler option for it (from memory: `-C llvm-args=-x86-branches-within-32B-boundaries`; check the spelling against `rustc -C llvm-args=--help-hidden`). It cannot be validated by timing on Zen 4; check with `objdump` that no hot jump crosses or ends on a 32-byte boundary, and that the Zen 4 time does not move.
- Gathers were dropped already; Downfall confirms that for SKX through ICX and is no argument on SPR and later.

### Gaps
- No measurement found of SSBD's cost in tight store-then-reload or table-reload loops on SKX/CLX/ICX/SPR; the published figures are whole-benchmark scores on client parts.
- No source read gives STIBP's cost for user code; it bears on indirect branches, of which our hot loops have none.
- The list of processors in Intel's jump-erratum paper and whether Ice Lake is exempt were not read from the primary document.

## 6. Loop shaping from codecs, parsers and packet frameworks

### Takeaway
The best-tuned decoders share four habits: hoist every bound out of the loop and over-write freely inside it, keep tables small enough for a shared L1, split work into short stages over a batch so each stage's code and data stay hot, and count µops per port rather than instructions. Of these, port-level analysis for the Intel targets, jump alignment and two-lines-per-zmm are the ones our notes do not show as tried.

### Cited Findings
**Entropy decoders**
- zstd's x86-64 assembly Huffman decoder: four interleaved streams, 5 symbols per stream per iteration (20 in all); "Computes how many iterations we can do safely" before the loop from output space and input headroom, so the body has no bounds checks; hot state (output pointers, bit containers, table, first input pointer) each in a register, colder pointers spilled to the stack and reloaded once per iteration; loop head aligned to 64 bytes. Release 1.5.1 reports Huffman literal decoding 1,164 to 1,500 MB/s with gcc-11 (+28.8%) and 1,006 to 1,504 MB/s with clang-13 (+49.5%) on an i9-9900K, 5 to 15% on whole decompression. — [huf_decompress_amd64.S](https://raw.githubusercontent.com/facebook/zstd/dev/lib/decompress/huf_decompress_amd64.S); [zstd v1.5.1 release notes](https://github.com/facebook/zstd/releases/tag/v1.5.1)
- Oodle's Huffman (Fabian Giesen): one stream is latency-bound at 6 to 7 cycles a symbol (table load 4 to 5 cycles) for 5 to 7 instructions, about 1 instruction per cycle on a machine that could run about 21 in that time; hence 3 or 6 streams, chosen as a compromise because more streams need more registers and are "more sensitive to microarchitectural issues". Code lengths capped at 11 bits so tables fit L1D and several symbols decode per refill without a branch (cost under 0.1% of ratio); a 15-bit table (about 96 KB) "would thrash L1D, especially with several hardware threads". One misprediction in one stream "wipes useful work done on all the other ones". Current decoders average "well under 2 cycles per symbol". — [Fabian Giesen, "Entropy coding in Oodle Data: Huffman coding"](https://fgiesen.wordpress.com/2021/08/30/entropy-coding-in-oodle-data-huffman-coding/)
- lz4: `LZ4_wildCopy8` "can overwrite up to 8 bytes beyond dstEnd" (16, 32, 64-byte variants likewise); the fast loop is "designed for modern OoO performance cpus, where copying reliably 32-bytes is preferable to an unpredictable branch" and runs only while the output is `FASTLOOP_SAFE_DISTANCE` from the end, with a careful loop for the tail; literals of at most 14 bytes are copied as 16 "hope compilers optimize better when copy by a register size". — [lz4.c](https://raw.githubusercontent.com/lz4/lz4/dev/lib/lz4.c)

**SIMD parsers**
- simdjson: two stages; stage 1 works on 64-byte blocks, "is essentially branchless, with a fixed cost per input bytes", and writes 8 separator indexes unconditionally per step, overwriting the surplus on the next (over 10% of stage 1 on some files); classification by two `vpshufb` nibble lookups; eight digits converted with multiply-adds in about seven instructions and at least 17 cycles of latency. Cost models on Skylake: stage 1 = 1.7 cycles per structural element + 0.62 per byte; stage 2 = 19 per float + 8.7 per structural + 0.31 per byte; 8.3 instructions per byte overall. Measured with hyper-threading disabled; AVX-512 left to future work. — [simdjson paper](https://ar5iv.labs.arxiv.org/html/1902.08318)

**Packet frameworks**
- VPP: with scalar processing "each packet incurs an identical set of I-cache misses" once the path exceeds the instruction cache; processing a vector of up to 256 packets one graph node at a time shares those misses, keeps the stack shallow, and enables "pipelining and prefetching to minimize read latency on table data". A node's function is a quad loop that prefetches the next four buffer headers with store intent while it handles four, then a single loop for the last 0 to 3; next-node choices go into an array and are enqueued once per frame. — [VPP, scalar vs vector processing](https://s3-docs.fd.io/vpp/24.02/aboutvpp/scalar-vs-vector-packet-processing.html); [VPP, VNET](https://s3-docs.fd.io/vpp/24.02/developer/corearchitecture/vnet.html)
- DPDK: bulk ring operations and bursts of 32 packets by default ("Performance is greatly improved when using bulk access operations"); per-core cache-aligned data; no allocation in the data path; build for the exact CPU. — [DPDK, Writing Efficient Code](https://doc.dpdk.org/guides/prog_guide/writing_efficient_code.html)

**Low-latency practice and tools**
- Trading-system tuning: turn hyper-threading off because it "increases contention on processor resources" and halves each thread's effective L1 and L2; explicit huge pages (an example run without them missed 28% of dTLB loads); `mitigations=off`. — [Erik Rigtorp, low latency tuning guide](https://rigtorp.se/low-latency-guide/)
- uiCA simulates basic blocks on every Intel Core generation from 2011 to 2021 and is "usually within 1% of measurement results"; IACA, llvm-mca, OSACA, Ithemal and CQA average 9 to 36% error. — [uiCA paper](https://arxiv.org/abs/2107.14210)
- Remedies for a port limit: replace port 5 shuffles with blends that run on ports 0 and 1, use memory-source broadcasts, measure with the per-port dispatch counters. — [Travis Downs, "Performance speed limits"](https://travisdowns.github.io/blog/2019/06/11/speed-limits.html)
- dav1d names its AVX-512 code path after Ice Lake (`avx512icl`), not Skylake-X. — [dav1d merge request 725](https://code.videolan.org/videolan/dav1d/-/merge_requests/725) (search summary)

### Inferences
Not shown as tried in positional.md, in the order we would try them:
1. **Port analysis for the scorer's cores.** Run the per-line loop and the 8-line step through uiCA for CLX and ICL (it covers both) and `llvm-mca -mcpu=sapphirerapids` for Golden Cove. Read µops per line per port; double them for a sibling pair. This replaces guessing about every item in section 2 and is the only way to rank changes that Zen 4 timing cannot see.
2. **Take µops off port 5.** Shuffle with zmm where two lines can share a register; blends, shifts and `vpternlog` in place of a shuffle where the move is fixed; constants broadcast from memory operands; AVX2 compares for masks if port 5 is the binding port.
3. **Jump alignment for the Cascade Lake erratum**, and the loop head at a 64-byte boundary as zstd does.
4. **`vpmuludq` in place of `vpmullq`** wherever the unscramble's factors allow.
5. **Spills in the 512-bit step.** zstd spills cold pointers once per iteration and keeps the hot state in registers; our decode spills about 40 vectors per 8 rows, which costs store-buffer entries (28 a thread on a CLX pair) and 4 to 5 cycle reloads on Intel where Zen 4 can mirror them. Thirty-two zmm registers and memory-operand constants give room to cut them.
6. **Stage batching in the VPP sense** has in effect been tried twice (newlines first; all fields cut before the kernels) and lost on Zen 4, where the µop cache is large and shared. It could still win on a CLX pair if item 1 shows the loop does not fit the decoded cache: split so that each stage's body is a few hundred µops and runs over 8 to 64 lines. Decide from the simulator's front-end result, not from the 7800X3D.
7. **Unconditional over-writes** (simdjson's eight indexes, lz4's wild copy) are the same idea as "compress in a register and store whole", which we have. The remaining use is the tail: compute the count of safe lines per chunk once, as zstd does, so the per-line exits disappear from the hot body.
- Interleaved streams (zstd's four, Oodle's six) answer latency-bound loops; ours is work-bound and "several lines in turn" measured nothing, which agrees with Giesen's account of when streams pay.
- Turning hyper-threading off is not ours to choose, and 8 workers measured best; the trading advice confirms only the cache-halving arithmetic used in sections 1 and 7.

### Gaps
- dav1d's source (bot protection) and x264's AVX-512 commit notes could not be read; nothing is quoted from them on register-width policy or alignment.
- Hyperscan and simdutf were not read.
- VPP's and DPDK's pages give no cycle counts for batching, and zstd's notes do not say why the assembly is faster.
- uiCA's paper predates Sapphire Rapids; its accuracy for Golden Cove, and llvm-mca's, is not established here. No source read tests any of these tools on code with two siblings.

## 7. Software prefetch and write patterns when two siblings share L1D and L2

### Takeaway
A sibling pair shares 32 KB of L1D and 1 MB of L2 on SKX/CLX (48 KB and 1.25 MB on ICX, 48 KB and 2 MB on SPR) and 10 to 12 line fill buffers; Intel's own rules are to block for a quarter to a half of the cache per thread, keep inner loops to about four write streams, and send write-combined data out a whole 64-byte line at a time from a small cached buffer, which is what the staged scatter does.

### Cited Findings
- Sizes: L1D 32 KB and L2 1 MB on Skylake-SP/CLX, 48 KB and 1.25 MB on ICX; SPR L2 2 MB. Zen 4 writes one 512-bit vector per two cycles, Ice Lake one per cycle. — [Hot Chips 32 Ice Lake-SP deck](https://www.hc32.hotchips.org/assets/program/conference/day1/HotChips2020_Server_Processors_Intel_Irma_ICX-CPU-final3.pdf); [Chips and Cheese, SPR](https://chipsandcheese.com/p/a-peek-at-sapphire-rapids); [Agner Fog, 24.10 and chapter 12](https://www.agner.org/optimize/microarchitecture.pdf)
- Fill buffers: 10 documented, 12 measured on Skylake and newer, competitively shared by the siblings; a sibling doing stores raises latency for both. They also hold the lines of streaming stores while they fill. — [ZombieLoad paper](https://arxiv.org/pdf/1905.05726); [Intel forum, write-combining buffers and fill buffers](https://community.intel.com/t5/Intel-Moderncode-for-Parallel/How-does-WC-buffer-relate-to-LFB/m-p/1174772) (search summary)
- Intel: "When coding functions that execute simultaneously on two threads, reducing the number of writes that are allowed in an inner loop will help take full advantage of write-combining store buffers"; if an inner loop writes to more than four arrays, split it; a write-combining buffer closed before it is full goes out as partial writes (8 transactions for 63 bytes; an effect "on the order of 20%" in some applications). Software write-combining: collect in a small buffer that fits L1, copy out when a line is full. — [Intel manual, 3.6.10, 8.5.5](https://www.cs.princeton.edu/courses/archive/fall13/cos217/reading/ia32opt.pdf)
- Intel: for two logical processors on one cache, block for "one quarter to one half of the cache size". — [Intel manual, 8.6.1, rule 31](https://www.cs.princeton.edu/courses/archive/fall13/cos217/reading/ia32opt.pdf)
- Measured (Intel): stores to lines that miss L1 and hit L2, interleaved with stores that hit L1, take 9 or 18 cycles each; prefetching the line or loading it first removes the cost. — [Travis Downs, Intel performance quirks](https://github.com/travisdowns/uarch-bench/wiki/Intel-Performance-Quirks)
- L2-to-L1 bandwidth: 1 line per cycle on Skylake and Skylake-X, 0.75 on Ice Lake client, 0.5 on Zen through Zen 3; L3 about 0.1 line per cycle measured on Skylake-X. — [Travis Downs, "Performance speed limits"](https://travisdowns.github.io/blog/2019/06/11/speed-limits.html)
- A 64-byte streaming store in uops.info's test: one per 17 cycles on SKX (17.6 on CLX), 4.9 on ICL, 5.95 on ADL-P. — [vmovntdq m512](https://uops.info/html-instr/VMOVNTDQ_M512_ZMM.html)
- Prefetch: Agner finds automatic prefetching "more efficient than explicit software prefetching in most cases" on Zen; VPP prefetches the next four buffer headers with store intent one iteration ahead. — [Agner Fog, chapter 24](https://www.agner.org/optimize/microarchitecture.pdf); [VPP, VNET](https://s3-docs.fd.io/vpp/24.02/developer/corearchitecture/vnet.html)

### Inferences
- Per-thread budget on a CLX pair by the quarter-to-half rule: 8 to 16 KB of L1D, 250 to 500 KB of L2. In the parse a worker touches its input chunk (256 to 512 KB in our tests) and 64 KB of staging lines (1,024 partitions x 64 B): 640 KB to 1.15 MB for a pair against a 1 MB L2. In the later stages two 256 KB slot arrays are 512 KB. Both are at or past the rule on SKX/CLX, tight on ICX (1.25 MB) and comfortable on SPR (2 MB). If the scorer is SKX/CLX, a 128 KB chunk and a 128 KB slot array are the sizes to test; our notes found chunk sizes from 128 KB to 1 MB equal on Zen 4, whose L2 is also 1 MB but whose L3 is 96 MB, so that result does not transfer.
- Staging lines: 1,024 x 64 B cannot be in L1 on any of these cores, so each record store is a store to an L1-missing, L2-present line among L1-hitting stores: exactly the 9-or-18-cycle case. The cures are a load or `prefetchw` of the staging line as soon as the partition is known (at the decode, 8 records ahead), or fewer partitions per pass so the lines stay in L1 (256 x 64 B = 16 KB is a thread's whole share on CLX; 128 is safer). Our Zen 4 result that fan-out is nearly free once staged does not settle this for a shared 32 KB L1D on Intel.
- Flushes: a full line sent with one 64-byte streaming store opens and closes a fill buffer at once, so a pair keeps at most a few of the 10 to 12 busy; never leave a partial line in a write-combining buffer across other work, and keep flushes of different partitions from interleaving half-lines (two 32-byte halves must be adjacent). On SKX/CLX the streaming store itself is slow (17 cycles in isolation), about 4 cycles a 16-byte record; if the simulator and a CLX run show the flush as hot, ordinary stores to the list tail with a `prefetchw` one line ahead are the alternative to measure there.
- Concurrent write streams per thread, as a working number for a pair: about 4 regular streams by Intel's old rule, and with 12 shared fill buffers no more than 4 to 5 lines of cache misses or open streaming lines in flight per thread. The counter tables of the later stages (increments scattered over dense per-worker tables) are loads before stores and so avoid the blind-store case; batching the loads first also suits SSBD.
- Addresses: give staging buffers, per-worker tables and the input chunk different offsets within a 4 KB page, so that the line window's loads and the staging stores do not alias modulo 4 KB systematically; 2 MB pages keep page walks (and their cancellation behind unknown-address stores on SKX/CLX) out of the scatter.

### Gaps
- No source gives a measured limit on write streams or staging-buffer size for a sibling pair on SKX/CLX, ICX or SPR; the four-stream rule is from the Pentium 4 era and the fill-buffer counts are from security papers.
- Fill-buffer counts for Ice Lake-SP and Golden Cove were not found (16 for Golden Cove is widely quoted but unsourced here).
- uops.info's streaming-store figure is an isolated test, not a streaming benchmark with a busy sibling; treat the 17 cycles as an upper indication only.
- The only way to close most gaps in this file is an hour on a Cascade Lake and an Ice Lake or Sapphire Rapids instance of 8 vCPUs (for example m5n.2xlarge and m7i.2xlarge), running the program with its paired harness and, where the hypervisor exposes them, the licence and per-port counters.
