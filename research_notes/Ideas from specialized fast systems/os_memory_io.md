# Operating-system costs on Linux: what very fast systems avoid, and what a short 8-thread batch run can still take

Reading guide. Tags used below: **[HOST]** needs root, a privileged container, a boot parameter or a host setting (not available to us); **[IN USE]** already in the program; **[DROPPED]** already measured and dropped; **[LISTED]** already in `alternatives.md` as untested; **[NEW]** not in the repository's notes as far as I could see. "Our" numbers come from `positional.md`, `x86.md` and `alternatives.md` (20M events: 230 ms wall, 1.81 s CPU, kernel about 20% = about 360 ms of CPU, of which copying the input about 145 ms, zeroing about 135 ms, the rest about 80 ms). Everything under "Cited Findings" was measured or stated by the linked source; everything about our program is under "Inferences". Several facts reached me only through a search summary of the linked page, not a full read; those are marked "(via search summary)".

## 1. Input: the cheapest way to consume several GB of page-cached file data from 8 threads

### Takeaway
There is no zero-copy route from the page cache into a process other than mapping the file; `splice`/`vmsplice`, `io_uring` and `O_DIRECT` do not provide one for cached data, so the choice stays "one copy into an L2-sized buffer" (what we do) against "page-table work per mapped page". The only thing that changes that trade is a host whose page cache holds large folios (XFS since 6.6 for written files, ext4 since 6.16), where a mapping costs far fewer faults; we cannot see the scorer's filesystem, so `pread` stays the robust choice and the 8% copy is mostly structural.

### Cited Findings
- Copy against bookkeeping, measured on a pipe: plain `write`/`read` moved 3.7 GiB/s; removing one copy (`vmsplice`) 12.7 GiB/s; removing both (`vmsplice` + `splice`) 32.8 GiB/s; the same on 2 MiB pages 51.0 GiB/s; with busy-polling 62.5 GiB/s (i7-8550U, Linux 5.17). In the baseline about 47% of the time was `pipe_write`, of which the copy about 24% and page allocation about 12%; once the copies were gone the cost was `get_user_pages_fast` walking per-4 KB `struct page`s, which is what huge pages halved — [How fast are Linux pipes anyway?](https://mazzo.li/posts/fast-pipes.html)
- The four access methods as ScyllaDB tabulates them: read/write "copying: yes, MMU activity: low"; mmap "copying: no, MMU activity: high"; direct I/O "none/none" but the application must cache and schedule itself. Page tables for a mapping cost 0.2% of the mapped size — [ScyllaDB: Different I/O access methods for Linux](https://www.scylladb.com/2017/10/05/io-access-methods-scylla/)
- CIDR 2022 (Crotty, Leis, Pavlo) concludes "MMAP is not a suitable replacement for a traditional buffer pool", naming page-table contention, single-threaded eviction and TLB shootdowns (I could only read the abstract page; the PDF did not parse) — [Are You Sure You Want to Use MMAP in Your DBMS?](https://db.cs.cmu.edu/mmap-cidr2022/)
- Warm-cache scan in Go: plain `mmap` came out slightly slower than chunked `read` into a buffer, attributed to minor faults; `MADV_WILLNEED` is a no-op when everything is cached and `MADV_SEQUENTIAL` only helps cold reads (single-author write-up, via search summary) — [Finding a needle in a 4 GB haystack](https://segflow.github.io/post/fast-file-search-go/)
- Counter-example: a Lucene benchmark of sequential reads of a 16 GB file that fits in memory had mmap ahead (334.9 against 218.6 ops/ms for `pread` through FFI), and `pread` ahead on a 64 GB file that did not fit (JVM, different workload; via search summary) — [Lucene issue #16044 comment](https://mid.mail-archive.com/issues@lucene.apache.org/msg95092.html)
- 1BRC, C entry with a mapped 13 GB file: the author estimated a page fault "every ~5500 cycles, or 2.25 microseconds" when the mapping was not prefilled (his own caveat: "probably somewhat wrong"); touching every page before parsing gave about 3%; `MAP_POPULATE` "would be nice" but holds the address-space lock for its whole duration; another entrant measured the unmap of the file at about 138 to 199 (unit not stated, apparently ms) regardless of thread count — [1BRC discussion #138](https://github.com/gunnarmorling/1brc/discussions/138)
- At 128 threads one C++ entry "finished faster than the OS could munmap the input file": `munmap` was over 50% of the time (via search summary of the same thread) — [1BRC discussion #138](https://github.com/gunnarmorling/1brc/discussions/138)
- Fault-around: a read fault on a file mapping maps the already-cached pages around it through `filemap_map_pages`; the window is `fault_around_bytes`, default 65536, range 4096 to 65536 — [mm: make fault_around_bytes configurable](https://lkml.iu.edu/hypermail/linux/kernel/1604.2/01377.html); [original fault-around commit](https://lab.nexedi.cn/kirr/linux/-/commit/a9b0f8618d46ba027243b8ecb5c2468a7112d235)
- Large folios on ext4 (regular files, merged for 6.16): average mmap read-fault latency fell from 3,634 ns to 2,005 ns because the readahead loop and the PTE-setting loop in `filemap_map_pages` run per folio; mmap write faults did not get fewer (max order 5, still one fault per page) and went from 958 to 1,596 ns each (via search summary) — [Re: ext4: enable large folio for regular file](https://lkml.rescloud.iu.edu/2507.0/05015.html); [series cover](https://patchew.org/linux/20250512063319.3539411-1-yi.zhang@huaweicloud.com)
- The same ext4 change was bisected as the cause of an 8 to 12% slowdown in one performance test during 6.16-rc1 to rc3 (resolution not found) — [lkml thread](https://lkml.indiana.edu/hypermail/linux/kernel/2506.3/05062.html)
- XFS/iomap creates large folios in the buffered write path since the 6.6 merge window; in the sequential-write benchmark it cut the number of folios by a factor of 256 — [LWN](https://lwn.net/Articles/937777/); [pull request](https://lkml.iu.edu/hypermail/linux/kernel/2307.2/01415.html)
- `MADV_POPULATE_READ`/`MADV_POPULATE_WRITE` (Linux 5.14) prefault page tables "without the actual memory access", on parts of existing mappings, returning errors instead of `SIGBUS` — [madvise(2)](https://man7.org/linux/man-pages/man2/madvise.2.html)
- `MADV_COLLAPSE` (Linux 6.1) synchronously collapses native pages into a huge page, "supports private anonymous pages, shmem pages, and file-backed pages", needs `CONFIG_READ_ONLY_THP_FOR_FS` for files, and "is independent of any sysfs setting under /sys/kernel/mm/transparent_hugepage" — [madvise(2)](https://man7.org/linux/man-pages/man2/madvise.2.html)
- `io_uring` on a warm cache: "When the 'I/O' is a memcpy from kernel page cache, io_uring's ring management costs more than the syscall it replaces"; the same harness had `io_uring` about 34 times faster than one `pread` thread for `O_DIRECT` random reads at depth 128 (single-author benchmark, via search summary) — [nazq/io-uring-bench](https://github.com/nazq/io-uring-bench)
- Jens Axboe: buffered reads, cached or uncached, still pay the page-cache-to-user memcpy; registered buffers with direct I/O have lower overhead (about 172 GB/s over 32 files in his test) (via search summary) — [lkml, RWF_UNCACHED read support](https://lkml.indiana.edu/2411.1/03214.html)
- What sets the kernel's copy speed. Zen 4: `rep movsb` is "as much as 25x slower" when `(dst-src) & 0xFFF` is small and non-zero: 4.2 GB/s against 111 GB/s for 8,192-byte copies on an EPYC 9374F — [glibc bug 30994](https://sourceware.org/bugzilla/show_bug.cgi?id=30994). Zen 3 and Zen 4 Genoa: 4 GB/s for 2,113-byte copies — [Launchpad 2030515](https://bugs.launchpad.net/bugs/2030515). A 2021 kernel thread about Intel says that in the 4 K-aliasing case forward `rep movsb` "seems to stay within a factor of 2 of optimal" while backward `rep movs` loses by a factor of 10 — [lkml](https://lkml.rescloud.iu.edu/2111.2/04911.html)
- The kernel's user-copy routine was rewritten in April 2023 to use `rep movsb` inline only on CPUs with FSRM ("x86: don't use REP_GOOD or ERMS for user memory copies"); after Eric Dumazet reported a copy regression, `rep movsb` for large copies on ERMS-only CPUs was restored in August 2023 ("x86: re-introduce support for ERMS copies for user space accesses"), and `rep movsq` for CPUs without ERMS after that — [commit adfcf4231b8c](https://github.molgen.mpg.de/mariux64/linux/commit/adfcf4231b8cbc2d9c1e7bfaa965b907e60639eb.patch); [commit 47ee3f1dd93b](https://github.com/ctrliq/kernel-src-tree/commit/47ee3f1dd93bcbe031539b1ecdaafb44b661c772); [regression thread](https://lkml.rescloud.iu.edu/2305.3/03859.html); [rep movsq patch](https://lore.kernel.org/all/CAHk-=wgemNj9GBepSEJXS5N99rr9wLkL668UC9TsKH45NnJ7Mg@mail.gmail.com/T/)

### Inferences
- **Our copy is already near its floor.** 1.7 GB in about 145 ms of CPU is about 12 GB/s per thread with eight threads sharing the memory bus; the pipe article's best copying path is the same order. The page-aligned buffer [IN USE] is exactly the cure for the Zen 4 `rep movsb` aliasing cliff the glibc bug describes; on Intel the cliff is reported as at most a factor of 2, so the alignment is still right and its effect on the scorer is simply smaller. Nothing here is new.
- **Host-kernel hazard we cannot fix:** a scorer on a Skylake or Cascade Lake Xeon (ERMS without FSRM) with a kernel from the window between the April 2023 rewrite and the August 2023 fix copies large blocks with a plain loop instead of `rep movsb`. It would slow every `pread` entry alike. [HOST]
- **A zero-copy route without per-4 KB faults exists only where the page cache holds 2 MB folios.** That needs a filesystem that makes large folios for the files as they were written or read (XFS: write path from 6.6; ext4: 6.16) and a 2 MB-aligned mapping, or a prior `MADV_COLLAPSE` on a file mapping (6.1, `CONFIG_READ_ONLY_THP_FOR_FS`), which itself copies the data once into a huge page that then stays in the cache. On a 5.15 or 6.8 ext4 host the cache is 4 KB folios and a mapping is what we measured: a fault per 64 KB and about 0.5 µs of page-table work per page, 3% more CPU than `pread` [DROPPED]. If the scorer runs ext4 on 6.16 or later, or XFS, the mapping's fault cost roughly halves (3,634 to 2,005 ns per fault in the ext4 measurement) and the mapping might win by up to the copy's 8% of CPU (at most about 18 ms of wall). That is untestable on our WSL2 5.15 kernel and unknowable for the scorer; I would not build on it. [NEW as a reason, not as an action]
- `MADV_COLLAPSE` on the input mapping is the one unexplored variant: collapse cost is a copy at kernel speed (the same work as `pread`), paid by the first run only, and the second and third runs would find huge folios in the cache. It depends on kernel 6.1+, a config option, the files not being open for writing, and it changes host state between scored runs. Speculative; I would not ship it without a host we can inspect. [NEW, speculative]
- `io_uring`: no gain for cached data (the copy remains, the ring adds cost), and it replaces about 5,500 system calls that cost well under a millisecond in total. Not applicable. `O_DIRECT`: bypasses the warm cache and reads the device; not applicable. `splice`/`vmsplice`: move page references between pipes and files, never into our address space; reading the pipe copies again. `readahead`/`posix_fadvise`: nothing to do on a warm cache (`alternatives.md` already says so for the cold case). `MADV_POPULATE_READ`: [DROPPED], measured no gain in `alternatives.md`.
- **Chunk size against L2 on the scorer [NEW as a caution]:** two workers share one core's L2 there. The copy's benefit is that the tokenizer reads from L2; with a chunk as large as the whole L2 and a sibling doing the same, half of each chunk is read back from L3. Our sweep (128 KB to 1 MB, no difference) was on a Zen 4 with 1 MB of L2 per worker. Where the choice is free, the smaller of the tied sizes (256 KB) is the safer default for the hyperthreaded case. Worth one paired run with the second copy on the siblings; expected effect small.

### Gaps
- No source gave a direct, same-machine comparison of `pread` into a reused buffer against a mapping with 2 MB page-cache folios. The CIDR paper's numbers (sequential scan GB/s, shootdown costs) could not be extracted.
- Unverified recollections, not sourced here: XFS has created large folios on the read path since 5.18; a PMD-sized page-cache folio under a 2 MB-aligned read-only mapping is mapped with one PMD entry; Docker's default seccomp profile has blocked the `io_uring` system calls since 2023; Skylake-SP/Cascade Lake have 1 MB of L2 per core and no FSRM, Ice Lake and later have FSRM.
- Whether `MADV_COLLAPSE` on a read-only bind-mounted file works from an unprivileged container was not tested or sourced.
- What ripgrep, DuckDB and ClickHouse report in numbers: I did not reach primary sources for them in the time available.

## 2. Fresh memory: zeroing, huge-page modes, per-VMA locks, reuse

### Takeaway
Zeroing a fresh 2 MB page runs at about 12 GB/s per thread on current kernels (512 separate 4 KB clears), and on Ubuntu-configured kernels before 6.13 a huge page was zeroed twice, so the 7.5% we see can be 15% on the scorer; none of it can be switched off from inside, so the only lever is touching fewer new pages (recycling blocks between stages). Per-VMA locks (6.4+) remove the fault-against-`mprotect` collision only between different mappings, and our design already makes no such calls after the reservation.

### Cited Findings
- Demand-fault throughput, `perf bench mem mmap -f demand -s 64GB`: 2 MB pages 11.76 GB/s on the current kernel, 25.34 GB/s (+115%) with a series that clears a huge page as one contiguous range; 1 GB pages 24.85 to 39.22 or 52.73 GB/s depending on the preemption model. On AMD Genoa, populate: 12.73 to 26.30 GB/s (2 MB), 26.23 to 61.17 GB/s (1 GB). The gain at 2 MB is attributed to hardware prefetchers working on a sequential clear; at 1 GB, on Zen, to extents larger than the last-level cache switching to a mode that does not allocate cache lines. Version 11 of the series was posted 2026-01-07 — [folio_zero_user: clear page ranges, v11](https://lkml.iu.edu/2601.0/06689.html)
- With `init_on_alloc=1` the page allocator zeroes every page it hands out, and multi-size and PMD huge pages were then zeroed again by `folio_zero_user()`, "for all arch"; order-0 pages were zeroed twice only on architectures without their own `vma_alloc_zeroed_movable_folio()` (x86 is "not impacted" for order 0). Fixed by commit 5708d96da20b in 6.13-rc1 — [patch](https://lkml.rescloud.iu.edu/2410.1/06900.html); [6.13-rc1 regression thread naming the commit](https://lkml.indiana.edu/hypermail/linux/kernel/2412.0/04651.html)
- `init_on_alloc` is on by default in Ubuntu kernels (reported from the 18.04 HWE kernel on; a user measured about 40% on an uncached `zfs send`; the maintainers kept it as hardening, removable only with the boot parameter `init_on_alloc=0`) — [Launchpad 1862822](https://bugs.launchpad.net/bugs/1862822); a later request to turn the default off exists — [Launchpad 2031324](https://bugs.launchpad.net/bugs/2031324). The kernel's help text: "most cases see <1% impact. Some synthetic workloads have measured as high as 7%" — [Kconfig.hardening](https://git.almalinux.org/almalinux/kernel/raw/branch/a9/security/Kconfig.hardening)
- Huge-page modes. `defrag`: `always` = a fault "will stall on allocation failure and directly reclaim pages and compact memory"; `defer` = wake kswapd/kcompactd, khugepaged installs huge pages later; `defer+madvise` and `madvise` (the default) = direct reclaim and compaction only for regions marked `MADV_HUGEPAGE`; `never` = fall back to small pages. Sizes other than the PMD size are "never" by default (multi-size huge pages are opt-in per size in sysfs). `PR_SET_THP_DISABLE` turns huge pages off for a process and is inherited across fork and exec — [Transparent Hugepage Support](https://docs.kernel.org/admin-guide/mm/transhuge.html)
- `MADV_HUGEPAGE` (2.6.38) enables huge pages for a range; `MADV_COLLAPSE` (6.1) needs at least one page of each 2 MB region already present and ignores the sysfs settings; `MADV_POPULATE_WRITE` (5.14) prefaults writable pages without a user access — [madvise(2)](https://man7.org/linux/man-pages/man2/madvise.2.html)
- Per-VMA locks: merged in the 6.4 merge window; the fault handler takes a read lock on the one mapping it touches and falls back to the address-space lock if that fails; at first only for anonymous pages not in swap. "Even if the lock itself is not contended, the constant cache-line bouncing hurts performance." The gain was "about 75% of that achieved with the speculative page-fault patches" — [LWN: Concurrent page-fault handling with per-VMA locks](https://lwn.net/Articles/906852/); stability problems right after 6.4 (Go builds), fixed in 6.4.x — [LWN](https://lwn.net/Articles/937943)
- Lock rules today: "you must obtain an mmap write lock first in order to obtain a VMA write lock"; a read lock "can be obtained without any other lock", is "entirely optimistic" and fails if "the lock is contended or a competing write has started", in which case the fault takes the address-space lock for reading; zapping (`MADV_DONTNEED`) needs only a stable mapping, so it runs under the weaker locks; `munmap` detaches mappings under the write lock and tears page tables down after downgrading — [Process Addresses](https://docs.kernel.org/mm/process_addrs.html)
- File-backed faults under the per-VMA lock came later: "Handle most file-backed faults under the VMA lock" (posted July 2023), then "mm: handle read faults under the VMA lock" — [series](https://patchwork.kernel.org/project/linux-mm/cover/20230724185410.1124082-1-willy@infradead.org); [commit](https://isrc.iscas.ac.cn/gitlab/mirrors/git.yoctoproject.org/linux-yocto/-/commit/12214eba1992642eee5813a9cc9f626e5b2d1815)
- Kernels on hosted runners in 2026 (GitHub Actions images, Azure kernels): Ubuntu 22.04 image 6.8.0-azure, Ubuntu 24.04 image 6.17.0-azure, Ubuntu 26.04 image 7.0.0-azure — [ubuntu22 image notes](https://newreleases.io/project/github/actions/runner-images/release/ubuntu22%2F20260505.131); [ubuntu24](https://newreleases.io/project/github/actions/runner-images/release/ubuntu24%2F20260505.126); [ubuntu26](https://newreleases.io/project/github/actions/runner-images/release/ubuntu26%2F20260622.50)
- Reuse as fast systems do it: DPDK's memory pool gives "each core ... full access to its own cache (without locks) of free objects", a small stack that is flushed by half when full and refilled by half when empty, so a freed object is the next one handed out on that core — [DPDK Mempool Library](https://doc.dpdk.org/guides/prog_guide/mempool_lib.html)

### Inferences
- **Cost per GB.** At the kernel benchmark's 11.76 GB/s a thread zeroes 1 GB of 2 MB pages in about 85 ms; `x86.md` measured 13 GB/s on one thread and 24 GB/s for the whole box on eight, so with all workers faulting at once each gets about 3 GB/s and zeroing is bound by the memory bus, not by instructions. Our 135 ms of CPU for about 1.05 GB fits that. With 4 KB pages the zeroing itself is the same bytes but adds about 260,000 faults per GB; `x86.md` measured `never` at 519 ms against 458.
- **The double-zeroing hazard [NEW].** If the scorer is an Ubuntu-family kernel older than 6.13 (5.15, 6.5, 6.8 and 6.11 all qualify) with the distribution's `init_on_alloc` default, every 2 MB page we fault is zeroed twice: the 7.5% becomes about 15% of CPU, and the page-cache pages allocated for our 60 MB of output are zeroed before we overwrite them. On such a host 4 KB anonymous pages are zeroed once (x86 is exempt for order 0), which narrows the gap between huge and small pages but, by our `never` measurement, probably does not reverse it. We cannot read the setting from inside the container (it is a build default, visible only in `/proc/cmdline` when overridden). The robust answer is the same either way: fault fewer new pages. A direct check is possible: time the first few 2 MB faults at start (about 170 µs each at 12 GB/s, about twice that when doubled).
- **Recycling blocks between stages is the one real lever left** [LISTED as `buf-pool`, est. −30 ms on the older layout]. Now that lists are chains of 4 KB chunks from one block per worker (commit `fc2dc7c`), a per-worker last-in-first-out stack of dead chunks, as in DPDK's per-core cache, lets the sessions and output stages write into pages that are already faulted and often still in L2. Ceiling: the whole 7.5% (about 17 ms of wall at 20M, more on a double-zeroing host); realistic: the share of the 1 GB that is first touched after the parse, which the stage timings suggest is a third to a half.
- **Do not hand memory back mid-run if the same worker will need memory again**: `MADV_DONTNEED` followed by a fresh fault pays an unmap, a TLB flush and a second zeroing for what a free-list would give for nothing. Release only what nothing will reuse (which the parallel release before exit [IN USE] already is).
- **Huge-page mode when the host is unknown.** `MADV_HUGEPAGE` on the reservation gives 2 MB pages under both `always` and `madvise` and is ignored under `never`; nothing an unprivileged process does at fault time gets huge pages under `never` (`MADV_COLLAPSE` is documented as independent of sysfs, but it works on already-present pages by copying them, a loss for memory written once). The one risk of the hint: with the default `defrag=madvise`, a hinted region is exactly the kind that stalls in direct compaction when the host has no free 2 MB page; an unhinted region under `always` would fall back to 4 KB at once. On a freshly booted or lightly loaded scorer this does not arise; on a long-running fragmented host it could cost milliseconds per fault. I judge the hint still right (the `never` penalty is 13% and certain, the stall is conditional). khugepaged plays no part in a 0.3 to 1 s process.
- **Per-VMA locks and us.** On 6.4+ a fault in one mapping no longer waits for an `mmap`/`mprotect`/`clone` on another, which would have removed the glibc-arena and thread-start collisions we found on 5.15. A change to the same mapping that is being faulted (heap growth by `mprotect` on a shared heap) still blocks its faults. Since we reserve once and make no address-space calls afterwards [IN USE], we are immune on any kernel; the finding only says the earlier fixes mattered most on old hosts. One residual: with 4 KB faults from eight threads in a single mapping, the lock's reference count is one cache line bounced by all of them, per-VMA or not; with 2 MB faults (about 500 in a run) it is irrelevant.
- `MADV_POPULATE_WRITE` from idle workers is an alternative to the touching loop [IN USE] with the same zeroing; it saves only the user-to-kernel transitions, which with 2 MB pages are a few hundred. No gain expected.
- **Writing output without faulting anonymous pages for it**: see section 6 (encode into a reused L2-sized block and `write` it in pieces).

### Gaps
- Whether the contiguous-clearing series (25 GB/s for 2 MB faults) has been merged, and into which release, was not confirmed.
- Whether anonymous huge-page faults were under the per-VMA lock from 6.4 or only later, and whether the first fault in a mapping (no `anon_vma` yet) falls back to the address-space lock: recollection says "from 6.4" and "yes", unsourced.
- Default kernels of other clouds and distributions (Amazon Linux 2023: 6.1 or 6.12; Debian 12: 6.1; Debian 13: 6.12; RHEL 9: 5.14 with backports; stock Ubuntu 22.04: 5.15, 24.04: 6.8) are from memory, not sourced here. Which distributions other than Ubuntu default `init_on_alloc` to on: not sourced.
- A recollection that 2025 kernels changed `MADV_COLLAPSE` to respect `enabled=never` contradicts the man page text quoted above; not verified.
- No source gave a clean per-fault cost for anonymous 4 KB faults on a current kernel; there is no unprivileged way to obtain unzeroed anonymous pages (recollection: `MAP_UNINITIALIZED` exists only for no-MMU kernels).

## 3. Exit: from the last output byte to `docker run` returning

### Takeaway
Inside a container the "child works, parent exits early" trick cannot hide teardown: when PID 1 of a PID namespace exits, the kernel kills every other process in it and PID 1's exit does not complete until they are gone, address spaces included. What we already do (release in parallel, then leave) is the available optimum; the rest of the tail is the container runtime's namespace and cgroup teardown, which on modern kernels is a few milliseconds at the runtime level and is out of our hands.

### Cited Findings
- When the init of a PID namespace exits, `zap_pid_ns_processes()` sends SIGKILL to every task in the namespace and, since a 2012 change, waits until all of them are gone so that PID 1 is the last task released — [kernel commit 6347e900](https://github.molgen.mpg.de/git-mirror/linux/commit/6347e90091041e34bea625370794c92f4ce71228.patch); a 2025 thread on the ordering ("PID namespace init releases its file locks before its children die") confirms children are still running briefly while PID 1 is exiting — [lkml](https://lkml.iu.edu/2510.0/02883.html)
- 1BRC: the "subprocess spawn trick" moved the leading GraalVM entry from about 2.552 s to 2.195 s in the community timeline (about 357 ms, the difference of two consecutive rows) — [#1BRC Timeline](https://tivrfoa.github.io/java/benchmark/performance/2024/02/05/1BRC-Timeline.html). Asked whether calling `_exit()` would skip the unmap, the C++ author answered that `time` still measures the unmap after an early exit; his fix was a new process that does everything, with the visible one returning once the output is printed — [1BRC discussion #138](https://github.com/gunnarmorling/1brc/discussions/138)
- A fork-per-range entry made the unmap parallel instead (each child maps part of the file); reaping the children cost it time ("reaping them raises it to 82ms"); a later entry chose no fork and noted that "unmapping eventually dominates" — [discussion #138](https://github.com/gunnarmorling/1brc/discussions/138); [discussion #495](https://github.com/gunnarmorling/1brc/discussions/495)
- `process_mrelease` exists so that a user-space out-of-memory killer can reap the memory of a process it has just killed, from the caller's own context instead of waiting for the victim; it is only allowed on a dying process — [LWN](https://lwn.net/Articles/864184); a 2026 proposal (`PROCESS_MRELEASE_REAP_KILL`) addresses the race where the victim has already entered `exit_mm` and the call fails with `ESRCH` — [lkml](https://lkml.iu.edu/2604.3/10775.html)
- `MADV_FREE` (4.5) frees lazily, under memory pressure; `MADV_DONTNEED` drops the pages at once — [madvise(2)](https://man7.org/linux/man-pages/man2/madvise.2.html)
- Runtime-level cost of a container's namespaces: `unshare -n true` (create and destroy a network namespace) 47.7 ms on kernel 4.5, 1.5 ms on 5.19.15 after `synchronize_net()` calls were replaced; an IPC namespace 10.9 ms to 0.1 ms after its teardown moved to a work queue (2020); a whole `crun run` went from about 160 ms to 28.9 ms (seccomp profile compilation fixed in libseccomp) to 5.6 ms with a cached filter — [Red Hat: speed of OCI containers](https://www.redhat.com/en/blog/speed-oci-containers)
- Older kernels created and destroyed only "about 4 or 7" network namespaces a second because of `synchronize_rcu` in cleanup — [lkml 2016](https://lkml.iu.edu/hypermail/linux/kernel/1611.1/03230.html)
- A 2026 preprint attributes only 8 to 10 ms (under 1.5%) of Docker's container start to namespace creation, the rest to the runtime chain and storage (single author, not reviewed; via search summary) — [arXiv 2602.15214](https://arxiv.org/abs/2602.15214)
- ext4 defaults: with delayed allocation, blocks are allocated at writeback, and writeback starts only after `dirty_expire_centisecs`; `auto_da_alloc` (default) detects replace-via-truncate and replace-via-rename and forces the new file's blocks to be allocated so the data reaches disk by the next journal commit (5 s default) — [ext4 admin guide](https://docs.kernel.org/admin-guide/ext4.html)

### Inferences
- **The exit-child trick [LISTED as `exit-child`, "probably nothing here"]: confirmed as useless for us, and slightly harmful.** We are PID 1. If PID 1 exits while a child still holds the address space, the kernel kills the child and PID 1's own exit waits for the child's teardown; the runtime's shim sees the container's init exit only after that. So the timed interval contains the same teardown plus a fork. The trick works in 1BRC only because the timing harness waits for the parent alone and the orphaned child is reparented outside the measurement. The line can be closed without a submission.
- `_exit` early changes nothing by itself: the waiter is notified after the address space is gone, which is what the 1BRC author observed and what our 100 ms single-thread teardown showed. `process_mrelease` cannot be used by a process on itself and reaps on one thread. `MADV_FREE` before exit would only move the freeing into the serial exit path; `MADV_DONTNEED` from all workers [IN USE] is right because zapping needs only the shared lock (section 2's lock rules).
- **What is left in the tail, in order:** freeing page tables and the (already emptied) mappings, closing descriptors, the namespace and cgroup teardown by the runtime, then the Docker daemon's own bookkeeping. On kernel 5.19 or later the namespace part is a millisecond or two; on kernels before 2018 to 2020 it was tens of milliseconds, identical for every entry. Page-cache writeback of the 60 MB is not waited for (no `fsync`, expiry-driven writeback) unless the output overwrites existing files on ext4, where the close of a truncated-and-rewritten file starts block allocation and I/O submission in our thread (see section 6).
- One thing still worth checking with `SS_TIMING=2`'s outside timer: that nothing large is still mapped at exit besides what is released (the binary, stacks, the descriptor of the last file). If the input were ever mapped again, its 4 KB entries (about 10 ms per GB in the 1BRC numbers, if their unit is ms) would come back into the tail.

### Gaps
- No primary source describes the exact mechanics of the 1BRC subprocess trick; the 357 ms is arithmetic on a community timeline.
- No source measures the interval between a container init's exit and `docker run` returning on a current Docker, nor the effect of the scorer's flags on it. The kernel version that introduced `process_mrelease` (recollection: 5.15) and its permission rules were not confirmed (the man page URL returned 404).
- That ext4 starts allocation at close for a truncated-and-rewritten file (as opposed to at the next commit) is recollection, not in the fetched text.

## 4. Scheduling: quota, spinning, a ninth thread, affinities, sibling hyperthreads

### Takeaway
With a cpuset of 8 CPUs and a quota of 8 CPUs the group cannot use more than its quota by arithmetic, so neither spinning nor a ninth thread can cause throttling on a kernel from 5.4 on (and at most about 1% on the affected older ones); spinning only costs the sibling hyperthread, and `pause` on Skylake-family Xeons (140 cycles) makes that cheap. Explicit one-worker-per-CPU affinity is what thread-per-core systems do; for us it is a cheap, unmeasured experiment with a small expected effect.

### Cited Findings
- Quota mechanics: period 100 ms by default; quota is handed to per-CPU run queues in slices of 5 ms (`sched_cfs_bandwidth_slice_us`); "Once a slice is assigned to a cpu it does not expire"; "all but 1ms of the slice may be returned to the global pool if all threads on that cpu become unrunnable"; a highly threaded group can briefly exceed its quota by the unused slice on each CPU; a group is also throttled when a parent's quota is used up; `cpu.stat` reports `nr_periods`, `nr_throttled`, `throttled_time`, `nr_bursts`, `burst_time`; a burst allowance exists (`cpu.cfs_burst_us` on cgroup v1) — [CFS Bandwidth Control](https://docs.kernel.org/scheduler/sched-bwc.html)
- The well-known false throttling: from 4.18, the 1 ms left on each CPU expired every period, stranding up to (n − 1) ms per period on an n-CPU machine (87 ms on 88 CPUs); fixed by removing slice expiry in mainline 5.4, backported to 4.14.154+, 4.19.84+, 5.3.9+, Ubuntu 4.15.0-67+ and 5.3.0-24+, RHEL 7 3.10.0-1062.8.1+, RHEL 8 4.18.0-147.2.1+. Advice: "use whole CPU quotas, as this decreases the number of schedulable CPUs available to the cgroup" — [Indeed: CPU throttling regression fix](https://engineering.indeedblog.com/blog/2019/12/cpu-throttling-regression-fix/); symptoms and reproducer (threads pinned one per CPU) — [Indeed: Unthrottled](https://engineering.indeedblog.com/blog/2019/12/unthrottled-fixing-cpu-limits-in-the-cloud/)
- `pause`: "about 10 cycles" before Skylake, "as many as 140 cycles" on Skylake (Intel optimization manual, quoted on lkml); 141 cycles on Skylake-X in Agner Fog's tables; a kernel developer notes the longer pause lets the sibling hyperthread make more progress while the first spins; Intel: what a spinning thread costs its sibling is the shared resources it wastes, and spin loops should be bounded by elapsed time, not by a fixed count of pauses (via search summary) — [lkml: spin loop primitives](https://lkml.indiana.edu/1704.0/04504.html); [Intel forum: pause cost and proper use in spin loops](https://community.intel.com/t5/Intel-ISA-Extensions/Pause-instruction-cost-and-proper-use-in-spin-loops/m-p/1137388); [mechanical-sympathy thread](https://groups.google.com/g/mechanical-sympathy/c/OeJeHrms7Ls)
- Thread-per-core practice: ScyllaDB's tuning keeps the server off CPU 0 "and its hyper-threading siblings", which take the interrupts — [ScyllaDB system configuration](https://opensource.docs.scylladb.com/stable/getting-started/system-configuration.html); a Seastar developer: where a CPU or hyperthread can be spared for interrupt handling alone it should be, because context switches hurt high-percentile latency — [seastar-dev](https://groups.google.com/g/seastar-dev/c/5EkX0KMh-TM); a DPDK-based product: "due to the polling operation of DPDK, using hyper-threaded cores can significantly degrade" packet processing unless sibling maps are correct or cores are pinned to avoid sibling contention — [Oracle SBC: hyperthreading and CPU affinity](https://docs.oracle.com/en/industries/communications/session-border-controller/10.1.0/installation/hyperthreading-cpu-affinity.html)

### Inferences
- **Throttling.** Eight CPUs can run at most 800 ms in a 100 ms period, which is the quota; a ninth runnable thread competes for those CPUs and adds no consumption. So quota exhaustion is impossible in steady state on 5.4+ (slices do not expire, leftovers carry over). On a 4.18 to 5.3 kernel without the backport, up to 7 ms per period could be stranded: under 1% of a run. Our measured 30 ms of throttling over 4 runs (`x86.md`) was with a quota of 8 over 16 logical CPUs and no cpuset, where threads can be spread over more than 8 CPUs and each holds a slice; it does not transfer to a pinned scorer. If the scorer's cgroup has a throttled parent, nothing we do changes it.
- **Spinning [IN USE, 300 µs].** It cannot throttle us; its cost is what it takes from the sibling that is still working. On the Xeon each `pause` idles the logical CPU for about 140 cycles, so a spin loop built on `pause` leaves the sibling nearly the whole core; on Zen 4 `pause` is much shorter and the spinner takes more. The loop must be bounded by time (it is). A possible refinement: no spinning at all for a worker whose sibling is known to be in the vector decode. Expected effect: under 1%.
- **Affinities [NEW as an experiment; `pin-socket` in `alternatives.md` is a different idea].** `sched_setaffinity` within the cpuset needs no privilege. One worker per logical CPU removes migrations (each costs an L2 refill of up to 1 MB and a cold TLB) and the case where two workers are placed on one CPU for a tick while another sits idle, which in a 230 ms run with a dozen pool rounds is the more plausible loss. The sibling map is readable in the container (`/sys/devices/system/cpu/cpuN/topology/thread_siblings_list`), which also allows serial sections to run on a core whose sibling is spinning or asleep. All eight hyperthreads are ours and busy, so the isolation advice of Seastar, DPDK and trading systems (keep the sibling idle, keep interrupts elsewhere) has nothing to give beyond that. Cost: 8 system calls at start. Measure with the paired harness; I expect 0 to 2%.
- A ninth thread: if the main thread sleeps while eight workers run, it is free; if it spins or works while eight workers are busy, it takes a hyperthread from one of them. Keep the main thread as one of the eight.

### Gaps
- No source measures explicit pinning against the default scheduler for a sub-second, 8-thread batch job; the expected gain above is my estimate. Seastar's own documentation of how it pins and sizes per-core memory, and DPDK's lcore guidance in its own performance guide, were not reached; the DPDK statement comes from a vendor's product manual.
- `pause` latency on Zen 4 and on Ice Lake or Sapphire Rapids: recollection only (shorter on Zen; still long on later Intel).

## 5. Container and mitigation costs

### Takeaway
None of the mitigations can be switched off by an unprivileged process, and for our system-call rate (about 5,000 calls per CPU-second) seccomp and page-table isolation together cost well under 1%; the two that can matter are store-bypass disabling in user code (already handled by loads-before-stores) and, on old kernels, per-fault overhead, which 2 MB pages already keep at a few hundred faults. A host with kernel 5.16+ or runc 1.2+ does not force store-bypass disabling on a default Docker container at all.

### Cited Findings
- seccomp per system call: `getpid` 646 ns native, 675 ns with one or two filters answered from the 5.11 bitmap cache, 732 and 752 ns with three and four filters run in full; about 20 ns per filter run. Docker's and systemd's filters decide mostly by system-call number, which is what the bitmap caches — [seccomp bitmap cache, v5 cover letter](https://lkml.indiana.edu/hypermail/linux/kernel/2010.1/02735.html); merged for 5.11, "reducing overhead for many real-world filters to O(1)" — [seccomp pull for 5.11](https://lore.kernel.org/lkml/202012151225.4881A90257@keescook/); [LWN](https://lwn.net/Articles/834785)
- Before 5.16 the x86 defaults `spec_store_bypass_disable=seccomp` and `spectre_v2_user=seccomp` turned store-bypass disabling and STIBP on for every thread that installs a seccomp filter; commit 2f46993d83ff (5.16) changed both defaults to `prctl`, so they are on only for tasks that ask — [patch and rationale](https://lkml.iu.edu/hypermail/linux/kernel/2011.0/05620.html); [seccomp pull for 5.16](https://lkml.iu.edu/hypermail/linux/kernel/2111.0/00943.html); Mozilla could "no longer reproduce the performance difference" after the change — [Mozilla bug 1649696](https://bug635044.bugzilla.mozilla.org/show_bug.cgi?id=1649696)
- A filter installed with `SECCOMP_FILTER_FLAG_SPEC_ALLOW` (Linux 4.17) does not trigger the store-bypass mitigation — [seccomp(2)](https://man7.org/linux/man-pages/man2/seccomp.2.html). runc sets it by default since 1.2.0-rc.1 (2024-04-03): "seccomp: refactor flags support; add flags to features, set `SPEC_ALLOW` by default. (#3588)" — [runc CHANGELOG](https://raw.githubusercontent.com/opencontainers/runc/main/CHANGELOG.md). (The 2020 kernel patch text claims runc and crun already did; the changelog is the primary source.)
- What a task can change: `PR_SPEC_DISABLE` turns a mitigation on for itself; `PR_SPEC_FORCE_DISABLE` is "Same as PR_SPEC_DISABLE, but cannot be undone", and a later attempt to enable speculation fails with `EPERM`; if the boot configuration does not allow per-task control the call fails with `ENXIO`; `PR_GET_SPECULATION_CTRL` reports the state — [Speculation Control](https://docs.kernel.org/userspace-api/spec_ctrl.html)
- STIBP cost when on for everything (Linux 4.20 before it was made conditional): perlbench in SPECint Rate 2006 lost 21% (Intel's Tim Chen); Rodinia was 22% and HMMer 30% faster with the mitigation off; the fix limited it to processes that ask and to seccomp threads — [The Register](https://theregister.com/2018/11/20/linux_kernel_spectre_v2_patch_slowdown_intel/); [Phoronix](https://www.phoronix.com/review/linux-420-stibp)
- Store-bypass disabling "isn't enabled globally by default since it can cause a performance penalty"; on AMD most tests showed no measurable change (via search summary) — [Phoronix, SSBD on Core i7](https://www.phoronix.com/review/intel-spectre-ssbd)
- Page-table isolation by system-call rate: under 0.5% below 10,000 calls per second per CPU, about 2% at 50,000, 5% measured at 75,000; with PCID (Linux 4.14+) a 100 MB working set at 5,000 calls per second per CPU cost about 0.5%, and with PCID plus huge pages the test came out 3% ahead; high page-fault rates add "a little more overhead" (no figure) — [Brendan Gregg: KPTI/KAISER Meltdown performance](https://www.brendangregg.com/blog/2018-02-09/kpti-kaiser-meltdown-performance.html)
- Starting a container with a seccomp profile cost 159 ms against 140 ms without on a 2017 stack, the difference being profile compilation in the runtime, not per-call cost; later 28.9 ms and 5.6 ms — [Red Hat: speed of OCI containers](https://www.redhat.com/en/blog/speed-oci-containers)

### Inferences
- **System calls**: about 5,500 `pread`s, a few hundred opens and closes and a few dozen writes per run. At 30 to 100 ns of seccomp cost each and a few hundred nanoseconds of entry and exit mitigations, that is 1 to 5 ms of CPU out of 1,810, on any kernel. Reducing the number of system calls is not worth an hour.
- **Faults** are where entry and exit costs would multiply: 1 GB on 4 KB pages is 260,000 kernel entries, each paying the page-table switch (Skylake-SP) and the speculation barriers; on 2 MB pages it is about 500. This is a second, host-dependent reason the `never` mode is the worst case and huge pages [IN USE] are the defence; under `never` the pre-touch by idle workers [IN USE] at least moves the entries off the critical path.
- **Store-bypass disabling.** Forced on only when the host kernel is older than 5.16 and the runtime is older than runc 1.2 (or sets explicit seccomp flags), or when an ancestor of the container process carries the force-disabled state. The last is the likely explanation for `x86.md`'s observation that Docker Desktop containers are mitigated even with `seccomp=unconfined` and `--privileged`: the state cannot be undone and the documentation gives no exec reset for it. On a stock Linux host with a 2024-or-later Docker it is probably off. The loads-before-stores loops [IN USE] cost nothing when it is off, so nothing changes; `prctl(PR_SET_SPECULATION_CTRL, PR_SPEC_STORE_BYPASS, PR_SPEC_ENABLE)` at start is harmless to try (it returns `EPERM` when forced, succeeds when the state was only `PR_SPEC_DISABLE`) but I expect it to gain nothing on the scorer. [NEW, very low value]
- **STIBP**: where forced (old kernel, old runtime, a CPU without enhanced IBRS) it slows indirect-branch-heavy code on hyperthreads by up to 20 to 30% in the cited tests; our hot loops are straight-line vector code with static dispatch, so the exposure is small. Keeping indirect calls out of the per-row paths (no trait objects, no function-pointer tables in the decode) is the only defence and largely already the case.
- Retpolines, IBRS on entry, MDS buffer clearing and page-table isolation are boot-time host settings. [HOST] Docker's own network and overlay layers do not touch our data path: the input and output are bind mounts onto the host filesystem.

### Gaps
- No source gave the per-fault cost of the entry/exit mitigations on current Xeons, or the user-code cost of store-bypass disabling on Skylake-family cores beyond "small in most tests"; our own scatter-loop measurements in `x86.md` are better evidence for our code.
- Whether the speculation-control state is inherited across `fork` and `execve` is not stated in the fetched documentation; the Docker Desktop explanation above is my inference.
- Which runc version current Docker Engine releases bundle (recollection: 1.2 or later since Docker 27.4/28) and which CPUs need page-table isolation (recollection: Skylake-SP yes, Cascade Lake and later no) were not sourced.

## 6. Output: creating and writing a few dozen MB into a mounted folder

### Takeaway
The cheapest path is plain `write` from memory that is already faulted and cached, in pieces of a few hundred KB from a reused block, one writer per file, into newly created files; mapping the output, `fallocate` and a single 60 MB buffer of fresh memory all add work. The whole output stage is 8 ms at 20M, so the reachable saving is a few milliseconds of CPU.

### Cited Findings
- In the buffered write path measured on a pipe, the copy was about a quarter and page allocation about an eighth of the system call's time; total 3.7 GiB/s with both copies — [How fast are Linux pipes anyway?](https://mazzo.li/posts/fast-pipes.html)
- A write fault on a file mapping costs about 958 ns per 4 KB page on ext4 (1,596 ns with large folios, still one fault per page) (via search summary) — [ext4 large folio thread](https://lkml.rescloud.iu.edu/2507.0/05015.html)
- ext4: with delayed allocation (default) blocks are allocated "just before ext4 writes out the block(s)", not at `write`; `nodelalloc` allocates "when the data is copied from userspace to the page cache"; `auto_da_alloc` (default) detects replace-via-truncate and replace-via-rename and forces the delayed blocks to be allocated; writeback begins after `dirty_expire_centisecs` — [ext4 admin guide](https://docs.kernel.org/admin-guide/ext4.html)
- Large folios in the buffered write path (XFS/iomap, 6.6) cut the folio count by 256 in a sequential-write test and removed lock contention at writeback; ext4 has them from 6.16 — [LWN](https://lwn.net/Articles/937777/); [ext4 series](https://patchew.org/linux/20250512063319.3539411-1-yi.zhang@huaweicloud.com)
- A plain system call costs on the order of 0.65 µs in a seccomp-filtered task on the test machine of the bitmap series — [seccomp bitmap cache cover letter](https://lkml.indiana.edu/hypermail/linux/kernel/2010.1/02735.html)
- With `init_on_alloc=1` every page the allocator hands out is zeroed first — [init_on_alloc double-zeroing patch](https://lkml.rescloud.iu.edu/2410.1/06900.html)

### Inferences
- **`write` in pieces from a reused block [NEW if the output is currently built whole in fresh memory].** Sixty MB of fresh anonymous pages cost a zeroing pass (5 to 8 ms of CPU at 8 to 12 GB/s, double on an Ubuntu kernel before 6.13), then our encode writes them, then the kernel copies them from DRAM. Encoding a column chunk into a per-worker block of 256 KB to 1 MB that stays in L2 and writing it out immediately removes the fresh pages and makes the kernel's copy read from cache; the extra 60 to 240 system calls cost about 0.1 ms. `pwritev` with the page headers and the column bytes as separate vectors avoids even the staging copy where a column's bytes already exist in final form (plain-encoded fixed-width columns).
- **Mapping the output file is worse than `write`**: every 4 KB page takes a fault of about 1 µs (15,000 faults for 60 MB, about 15 ms of CPU), a new page-cache page behind a mapping must be zeroed before we fill it, and the file must be sized first with `ftruncate`. Not applicable.
- **`fallocate` adds work in the timed window** on a delayed-allocation filesystem: it performs at `write` time the block allocation that would otherwise happen at writeback after we are gone, and the preallocated extents must be converted when written. Not applicable. `O_TMPFILE` plus `linkat` saves nothing over creating the file by name.
- **New names, not truncation.** Overwriting files left by an earlier run pays for freeing their page cache at `O_TRUNC` (we saw it on tmpfs) and, on ext4, triggers the replace-via-truncate handling at close. If the scorer's output folder can hold old files, `unlink` is no cheaper than truncation (the same pages are freed), so there is no trick here beyond knowing that a fresh folder is the fast case and benchmarking with one (we do).
- **One writer per file, files in parallel** [IN USE: a file per worker]. Buffered writes to one file take turns on the inode's lock; separate files do not interact.
- 60 MB of dirty pages is far below any dirty-throttling threshold on a host with GBs of memory, so `write` never blocks on the device; do not `fsync`.

### Gaps
- No source measures `write` against mapped output for tens of MB on a current kernel, or the close-time cost of ext4's replace-via-truncate; the judgments above combine the cited per-page figures with our stage timings. That buffered writes to one file are serialized by the inode lock is recollection, not sourced here.
- How the scorer mounts the output folder (bind onto ext4, XFS, overlay or tmpfs) is unknown; on tmpfs there is no writeback at all and the page allocation plus copy is the whole cost.

## 7. Static-allocation designs: anything beyond "reserve once, never call the system again"

### Takeaway
What carries over is not the reservation (done) but what these systems do inside it: one pool whose blocks serve every stage in turn, sized by arithmetic from the input estimate; a per-core last-in-first-out cache so the next block handed out is the one just freed (already faulted, still in cache); and capacity asserted rather than grown, so growth on a worker thread is a bug that shows up in tests.

### Cited Findings
- TigerBeetle allocates all memory at startup; the amount "is simply calculated with a bit of addition and multiplication at startup" from configured limits; collections are used in fixed-capacity form (`addOneAssumeCapacity`, `putAssumeCapacityNoClobber`) so that accidental growth is a visible bug; message buffers come from pools shared by the journal, the client table, the pipeline and the connection queues, sized as the sum of each user's needs, with assertions that a free message is always available ("static allocation is a force multiplier for fuzzing!"); records are fixed-size, 128 bytes, cache-line aligned, with no serialization step (the bytes on the wire are the struct); "Reducing the amount of memory used means fewer cache lines fetched from main memory in general" — [A Database Without Dynamic Memory Allocation](https://tigerbeetle.com/blog/2022-10-12-a-database-without-dynamic-memory/)
- DPDK memory pools: the shared ring costs a compare-and-set per access, so "each core has full access to its own cache (without locks) of free objects"; the cache is a small stack, flushed by half to the pool when full and refilled by half when empty; buffers can sit idle in one core's cache (the trade-off); object start addresses can be padded so that they spread over memory channels and ranks, because "Only the first 64 bytes are accessed" in packet workloads — [DPDK Mempool Library](https://doc.dpdk.org/guides/prog_guide/mempool_lib.html)
- ScyllaDB/Seastar takes cache control, I/O scheduling and thread scheduling into user space ("the application has full control over both running threads and waiting I/O"), at the stated cost of complexity — [ScyllaDB: I/O access methods](https://www.scylladb.com/2017/10/05/io-access-methods-scylla/)

### Inferences
- **A pool across stages, not a region per purpose [LISTED as `buf-pool`; the sizing rule and the last-in-first-out order are the additions].** TigerBeetle's message pool is one set of buffers that the journal, the pipeline and the network all draw from; ours would be the 4 KB chunks of commit `fc2dc7c`, returned to the worker's stack when a list is consumed (a partition after placing, a person's clicks after sessions) and drawn again by the next stage. With a per-worker stack as in DPDK, the block handed out is the one freed most recently: no fault, no zeroing, and usually in L2. This is the concrete form of "touch fewer new pages" in section 2 and is where I would expect most of the avoidable kernel time to be (up to the zeroing's 7.5%, plus the cache misses of writing into cold zeroed pages).
- **Capacity by arithmetic, growth as a bug.** We already estimate rows from the first lines. Sizing every list, table and output block from that estimate with a stated margin, and making the fallback path (`Parts::spill`, the `user_daily` columns that reallocated 800 times) count and report in `SS_TIMING` rather than silently grow, is TigerBeetle's `AssumeCapacity` discipline; it protects the "no system call after the reservation" property against regressions.
- **Fixed-size, aligned records with no re-serialization** between stages: already the shape of the positional records; the cited systems confirm it rather than add to it.
- **Per-core ownership** (Seastar's shared-nothing memory, DPDK's per-core caches): each worker's region is faulted by the worker that will use it [IN USE via pre-touch], which is also what keeps memory on the right node if the scorer's 8 CPUs ever span two; with explicit affinities (section 4) the association is exact.
- DPDK's channel and rank padding addresses headers of many equal-sized objects all landing on the same memory channel; our writes are sequential streams, so it does not apply. Its hugetlbfs backing and Seastar's locked, pre-reserved memory need host configuration. [HOST]

### Gaps
- LMDB (single-level store over a read-only mapping) was not researched; its relevant idea, reading through a mapping with no copy, is covered and judged in section 1.
- Seastar's allocator documentation (per-core pools, huge-page backing, cross-core free queues) was not reached; the statements above about it come from the ScyllaDB article and general description, not from its design documents.
