# Whole-program tricks of speed-contest entries (1BRC, highload.fun, FizzBuzz and similar)

Reading note for the report writer: pages were read through a summarising fetch tool, so short quotes below are as that tool returned them; where two sources or a source and its own code disagree, it is said in place. "Ours" means the shopping-sessions program as described in the brief and in `positional.md` / `alternatives.md`. Everything under "Inferences" is my judgment, not a source's measurement.

## 1. One Billion Row Challenge: what the top entries did at the whole-program level

### Takeaway
Almost every whole-program trick of the 1BRC winners is either already in our program (work handed out from a shared counter, a kept pool, parallel release, `pread`, static binary) or exists only to work around a cost we no longer have (the serial unmap of a 13 GB mapping, SMT being switched off on the judge). The only structurally different design is austindonisan's: worker processes instead of threads, so that page-table work is never shared; it is the one idea here we have neither built nor measured, and I judge it a poor fit for a pipeline whose stages exchange data.

### Cited Findings

**Correction to the brief.** austindonisan's C entry is AVX2 on Zen 2, not AVX-512 ("AVX2 is required") — [repo README](https://github.com/austindonisan/1brc). The AVX-512 native entry is charlielye's C++ on an m7i.48xlarge — [discussion #495](https://github.com/gunnarmorling/1brc/discussions/495). dannyvankooten's blog post does not use or mention the fork trick, `MAP_POPULATE` or `madvise` — [dannyvankooten](https://www.dannyvankooten.com/blog/2024/1brc/).

**The judge.** Main board: eight cores of a 32-core AMD EPYC 7502P (Zen 2); the bonus board used all 32 cores / 64 threads "with SMT enabled and turbo boost enabled", which implies both were off for the main board. Winners: thomaswue 1.535 s, artsiomkorzun 1.587 s, jerrinot 1.608 s on 8 cores; jerrinot 0.323 s, thomaswue 0.326 s on 32 cores / 64 threads — [results post](https://www.morling.dev/blog/1brc-results-are-in/). Five runs each, fastest and slowest discarded, file on a RAM disk — [Morling's talk](https://www.infoq.com/presentations/1brc/). The 8 cores were selected with `numactl --physcpubind=0-7` — [discussion #138](https://github.com/gunnarmorling/1brc/discussions/138).

**The subprocess trick (parent exits before the mapping is unmapped).**
- Mechanism in the winning entry: `main` without `--worker` re-launches its own command line with `--worker`, pipes the child's stdout, copies it to its own stdout (`transferTo`) and returns at EOF; the child prints, then calls `System.out.close()`, which is the EOF, and only afterwards exits and has its mapping torn down. The file is mapped once with a global arena and never unmapped explicitly — [thomaswue source](https://github.com/gunnarmorling/1brc/blob/main/src/main/java/dev/morling/onebrc/CalculateAverage_thomaswue.java); the same in [artsiomkorzun source](https://github.com/gunnarmorling/1brc/blob/main/src/main/java/dev/morling/onebrc/CalculateAverage_artsiomkorzun.java).
- Size of the cost it hides: about 100 ms of unmapping out of about 200 ms of start-and-cleanup overhead on a 1.8 s run (Hetzner CCX33) — [Topolnik, QuestDB](https://questdb.com/blog/billion-row-challenge-step-by-step/). Ragnar measured the unmap of the 13 GB mapping at about 180 ms on the main thread (i7-10750H); mapping per thread did not help "because `munmap` takes a process-wide lock"; 2-3x as many threads reduced it to about 100 ms — [curiouscoding.nl](https://curiouscoding.nl/posts/1brc/). lehuyduc: "At 128 threads, the program finishes the challenge faster than the OS can `munmap` the input file", unmap "over 50% of the time"; "Even if you `exit(1);` early, `munmap` will still be measured by `time`" — [discussion #138](https://github.com/gunnarmorling/1brc/discussions/138).
- Whether it works as PID 1 of a container: when a PID namespace's init terminates, "the kernel terminates all of the processes in the namespace via a SIGKILL signal" — [pid_namespaces(7)](https://man7.org/linux/man-pages/man7/pid_namespaces.7.html). The kernel does this inside init's own exit: `zap_pid_ns_processes()` signals every remaining task ("signal and wait for them to exit"), reaps children with `kernel_wait4()` in a loop, then sleeps until the namespace's PID count is down to init's own ("Once all of the other tasks are gone from the pid_namespace ... `free_pid()` will awaken this task") — [kernel/pid_namespace.c](https://github.com/torvalds/linux/blob/master/kernel/pid_namespace.c).

**Processes instead of threads (austindonisan, 0.577 s on an 8-core Zen 2 GCP instance; single runs 0.520-0.525 s).**
- "fork() is used over threads to allow for parallel unmapping"; separate address spaces let the kernel alter each process's page table "fully in parallel". Workers are forked as a tree; each copies its result into a slice of a `MAP_SHARED|MAP_ANONYMOUS` block and writes one byte to a pipe; each parent `poll()`s its children and merges as results arrive, so it never waits for a child to exit. The root prints and returns; children are left as orphans unless a flag forces `wait()`, which "adds about 20ms" — [discussion #710](https://github.com/gunnarmorling/1brc/discussions/710), [1brc.c](https://github.com/austindonisan/1brc/blob/master/1brc.c). (The write-up says fan-out 8; the code's constant is 16.)
- His reason, from the earlier thread: `mmap` and `munmap` "hold a process-wide address space lock", and `MAP_POPULATE` holds it for its whole duration — [discussion #138](https://github.com/gunnarmorling/1brc/discussions/138).
- Hot tables stay in private memory "because shared memory has huge pages disabled by default on Linux"; they get `madvise(MADV_HUGEPAGE)` and one `madvise(MADV_POPULATE_WRITE)` over the whole arena, except one table: "The offsets table wants 4 KiB pages; the rest wants 2 MiB huge pages". Keeping the tables in the TLB is "a significant performance win" — [1brc.c](https://github.com/austindonisan/1brc/blob/master/1brc.c), [discussion #710](https://github.com/gunnarmorling/1brc/discussions/710).
- Input: each worker reserves a 4 GiB anonymous window once and maps each piece of the file into it with `MAP_PRIVATE|MAP_FIXED`, so the next piece replaces the last without a `munmap`; the 4 KiB before the data holds dummy rows that finished lanes keep parsing — [1brc.c](https://github.com/austindonisan/1brc/blob/master/1brc.c). dzaima proposed the same `MAP_FIXED` overlay for threads and saw no difference on a 1.38 GB, 2-thread test — [discussion #138](https://github.com/gunnarmorling/1brc/discussions/138).
- Each leaf pins itself with `sched_setaffinity` to the n-th allowed CPU: "Very helpful at high core counts, slightly harmful at low ones"; "For hyperthreaded CPUs, logical CPU numbers must not be interleaved" — [1brc.c](https://github.com/austindonisan/1brc/blob/master/1brc.c).
- A prefetch slightly ahead of the read position: about 6% (8% on the 10K set) on Zen 2, 35% on an older Haswell. Clang 17 against GCC: GCC "~15% slower". Output: "One big buffer + a single fputs" — [discussion #710](https://github.com/gunnarmorling/1brc/discussions/710), [1brc.c](https://github.com/austindonisan/1brc/blob/master/1brc.c).

**Unmapping without a second process (charlielye, C++ with AVX-512, m7i.48xlarge, 64 threads).** The file is processed as 8 linear super-chunks by a pool of core-pinned threads, each super-chunk unmapped when the next begins; hash-table memory is initialised over the pool. Phases: setup 15.6, parallel 137.1, combining 4.3, writing 0.8, total 157.7 ms, 198.6 ms with the unmap; "the implementation of this solution was mostly expended on dealing with unmap" — [discussion #495](https://github.com/gunnarmorling/1brc/discussions/495). buybackoff staggered the unmaps instead (each thread's chunk split unevenly, because `munmap` "is slow and locks all threads"): 1.945 s to 1.814 s on a 6C/12T desktop at a fixed 2.5 GHz — [buybackoff](https://hotforknowledge.com/2024/01/13/1brc-in-dotnet-among-fastest-on-linux-my-optimization-journey/).

**Reading against mapping.** noahfalk (fastest managed entry, 1.381 s on a Hetzner CCX33 against about 2.5 s for the top Java entries on similar hardware) found file reads faster than a mapping "even on Linux": memory throughput is "a bit faster with memory mapping" but not enough "to outweigh some fixed costs of creating and releasing the mapping" — [noahfalk README](https://github.com/noahfalk/1brc/blob/main/README.md). buybackoff found the opposite, a no-mmap variant "visibly slower, but not too much", the copy costing "~200 msec at max CPU bandwidth" — [buybackoff](https://hotforknowledge.com/2024/01/13/1brc-in-dotnet-among-fastest-on-linux-my-optimization-journey/). dannyvankooten tried to get huge pages for the input by reading the file into a `MAP_HUGETLB` anonymous mapping: slower than letting the kernel fault the file mapping, with page faults about 23.5% of his profile (Ryzen 4800U) — [dannyvankooten](https://www.dannyvankooten.com/blog/2024/1brc/). A Go entry reading with `File.Read` found 4 MB buffers best (0.985 s for the read alone, against 1.008 s at 1 MB and 1.32 s at 64 MB, Ryzen 7900X on Windows), and passing chunks through a channel cost 0.28 s against workers reading for themselves — [r2p.dev](https://r2p.dev/b/2024-03-18-1brc-go/).

**Chunk size and work stealing.** thomaswue and artsiomkorzun: `SEGMENT_SIZE` 2 MiB, claimed with one atomic add on a shared cursor, each segment cut in three for three interleaved cursors — [thomaswue source](https://github.com/gunnarmorling/1brc/blob/main/src/main/java/dev/morling/onebrc/CalculateAverage_thomaswue.java), [artsiomkorzun source](https://github.com/gunnarmorling/1brc/blob/main/src/main/java/dev/morling/onebrc/CalculateAverage_artsiomkorzun.java). Gain of stealing over one chunk per thread: 1.8 s to 1.7 s — [Topolnik](https://questdb.com/blog/billion-row-challenge-step-by-step/). Reason given: "one of those CPU cores will always be the slowest"; 2 MB was the best size found on the judge — [Morling's talk](https://www.infoq.com/presentations/1brc/). The native leaders did not steal: austindonisan "Each worker completes its entire chunk with no re-leveling" — [discussion #710](https://github.com/gunnarmorling/1brc/discussions/710); Ragnar one chunk per thread — [curiouscoding.nl](https://curiouscoding.nl/posts/1brc/).

**Merging.** artsiomkorzun's workers merge among themselves as they finish: a thread tries to compare-and-set its table into a shared slot, and if one is already there takes it, merges and retries; the main thread only joins — [artsiomkorzun source](https://github.com/gunnarmorling/1brc/blob/main/src/main/java/dev/morling/onebrc/CalculateAverage_artsiomkorzun.java). lehuyduc: parallel aggregation saves about 28 ms at 128 threads, a second level 2.5 ms more — [discussion #138](https://github.com/gunnarmorling/1brc/discussions/138). charlielye reduces in log2(threads) levels — [discussion #495](https://github.com/gunnarmorling/1brc/discussions/495).

**Hyperthreads and interleaved cursors.**
- Three cursors per thread was the judge's optimum with SMT off; thomaswue tried four — [Morling's talk](https://www.infoq.com/presentations/1brc/).
- Ragnar (i7-10750H, 6C/12T): an early version gained 10% from HT (12 threads, 1.34 s); after 4-way interleaving the final code gains nothing: 0.90 s on 6 threads with HT off, 0.92 s on 12 threads with HT on, 0.97 s on 6 threads with HT on; IPC 2.39 per thread without HT against 1.33 with; "hyperthreading actually slows down the code" — [curiouscoding.nl](https://curiouscoding.nl/posts/1brc/).
- buybackoff: two interleaved flows per thread (his last step, "per-core parallelism", 1.791 s to 1.491 s) make "HT and non-HT basically the same"; 3 or 4 flows add nothing — [buybackoff](https://hotforknowledge.com/2024/01/13/1brc-in-dotnet-among-fastest-on-linux-my-optimization-journey/).
- lehuyduc tunes for two threads per core (keeps changes that help at 2x physical threads even if they cost at 1x); HT gave him about 62% and 38% on two AMD machines against about 10% for Ragnar's code on Intel; his README offers "a trick to practically disable hyperthreading" that is "Sometimes it's faster, sometimes it's worse" — [discussion #138](https://github.com/gunnarmorling/1brc/discussions/138), [repo](https://github.com/lehuyduc/1brc-simd).
- charlielye (AVX-512): "my performance pretty much universally degrades when I go past physical core count" on the default data, yet on the cache-missing 10K-key data 96 threads beat 64 (390.8 against 459.5 ms). sharpobject's explanation in the same thread: SMT "lets the core schedule 2 streams of instructions instead of 1"; if one already saturates a port "you won't gain anything" — [discussion #495](https://github.com/gunnarmorling/1brc/discussions/495).
- noahfalk parses 8 rows per thread in step (better than 4, "not by much") and computes the table slot early, prefetches it, and parses the number while it arrives — [noahfalk README](https://github.com/noahfalk/1brc/blob/main/README.md). austindonisan: 8 streams per worker, one accumulator copy per stream (the tables leave L1, "L2 bandwidth is sufficient"); 14.5 cycles a row at IPC 2.8 — [discussion #710](https://github.com/gunnarmorling/1brc/discussions/710).

**Branchless only because of misprediction rates.** Topolnik simulated a 2-bit predictor on the real name lengths: branching on `nameLen > 8` mispredicts about 50%, on `> 16` about 2.5%; that change took 2.4 s to 1.8 s (misses 0.657 to 0.084 a row, IPC 1.89 to 2.19); rule of thumb "a single branch misprediction costs as much as 10-15 instructions" — [Topolnik](https://questdb.com/blog/billion-row-challenge-step-by-step/). Conversely min/max were left as branches by Ragnar (1.42 to 1.37 s) and buybackoff, since updates become rare after a handful of rows — [curiouscoding.nl](https://curiouscoding.nl/posts/1brc/), [buybackoff](https://hotforknowledge.com/2024/01/13/1brc-in-dotnet-among-fastest-on-linux-my-optimization-journey/).

**Pre-touching input pages.** austindonisan reported about 3% from each thread touching every page of its part of the mapping before parsing, then withdrew the per-cycle reasoning because TurboBoost was off during the test — [discussion #138](https://github.com/gunnarmorling/1brc/discussions/138). `MAP_POPULATE` appears in none of the 1BRC entries read.

### Inferences

| Technique | Where we stand | Judgment for our program |
| --- | --- | --- |
| Subprocess / orphaned children | `exit-child`, untested in `alternatives.md` | Cannot hide anything: our binary is PID 1, and the kernel finishes killing and waiting for every other process of the namespace inside PID 1's exit, before `docker run` can see it end. Nothing left to hide either: parallel release already ends the process 3 ms after its last output. Drop without a test. |
| Worker processes instead of threads | not built | The only new structural idea. It would make the dropped per-chunk release of a mapped input free of cross-worker TLB flushes and take the address-space lock out of every fault. But our stages hand lists between workers, so the lists would live in shared memory, which gets no 2 MB pages by default (austindonisan's own reason for keeping tables private). The most it could return is the `pread` copy (8% of cycles) less the faults of a mapping, and our own measurement already puts mapping and `pread` within 2-3%. Not worth building. |
| `MADV_POPULATE_WRITE` over a worker's region instead of a byte written per page | not used (only `MADV_POPULATE_READ` on input was measured) | One call per region instead of one fault per 2 MB page: microseconds. The zeroing itself (7.5% of cycles) is unchanged; no contest entry avoids zeroing, they only move it. |
| Page size chosen per region (4 KiB for a sparsely written table, 2 MiB for dense ones) | partly, through 4 KB chunk chains | Applies to any region reserved larger than written: `MADV_NOHUGEPAGE` on it means only written pages are zeroed. Worth a look for whatever is still reserved with a margin (click overflow, slots); a few ms at most. |
| One worker pinned to each logical CPU | not used (`pin-socket` untested) | Eight `sched_setaffinity` calls at pool start. austindonisan found it slightly harmful at 8 workers, so expect nothing; cheap to settle with the paired harness. |
| Interleaved cursors, 2 MB stealing, prefetch ahead of a mapped input, staggered unmaps, concurrent merge, single output write, static binary | in place or measured | Nothing new. The contest data agrees with our result: interleaving is a substitute for a sibling thread, not an addition to it (Ragnar and buybackoff both lose the SMT gain once they interleave). |

- An idea no entry tried, suggested by the SMT findings above and by our parse taking twice as long with two workers per core: give the two threads of a core different jobs during the parse. SMT helped these entries where a thread waits (charlielye's 10K-key run takes 15% less time on 96 threads than on 64; lehuyduc reports 62%) and not where it is bound by execution ports (charlielye's default run, Ragnar's final code). The kernel's share of our parse (the `pread` copy, the zeroing of the next list pages) is memory work that competes least with a sibling in the 512-bit decode, and both threads share the core's L2, where the decode wants the chunk. Four decode threads with four helper threads that read the next chunk and fault the next output pages is not among the configurations we dropped (those were fewer workers, all doing the same thing). I cannot put a number on it; the bound is the kernel's share of the parse.
- Morling's talk attributes the 2 MB segment to "a 16 MB L2 cache and eight threads"; 16 MB is that CPU's L3 per four cores as far as I know, so read it as "a thread's share of L3", which matches our own note that 0.25-1.0 x L3 per thread is the reported optimum.

### Gaps
- thomaswue's header comment and pull requests, which state his own measured gain for the subprocess and for three cursors, could not be retrieved verbatim; the 100 ms figure is Topolnik's.
- What lehuyduc's "trick to practically disable hyperthreading" is: not described in the README text retrieved.
- jerrinot's, royvanrijn's and nietras's own write-ups were not read; nietras's read-against-map numbers are known only through noahfalk's and buybackoff's remarks.
- No 1BRC entry has large intermediate data (their state is a few MB of hash tables), so none says anything about our 1.2 GB of freshly zeroed pages.
- That `docker run` returns only after PID 1 is reaped is not from a source read here; only the kernel half (init waits for the namespace to empty) is cited.

## 2. highload.fun: whole-program and kernel tricks of the top solutions

### Takeaway
The highload.fun toolkit is small and single-threaded: map stdin (a file in RAM) with `MAP_POPULATE`, link statically without PIE and leave with `_exit`, then shape the memory access pattern to the hardware prefetcher. Only the last is not already in our program, and it pays only for a loop bound by one core's memory bandwidth.

### Cited Findings
- The platform's own advice: "`STDIN` is a file in RAM"; get its size with `lseek(0, 0, SEEK_END)` and `mmap(0, fsize, PROT_READ, MAP_PRIVATE | MAP_POPULATE, 0, 0)`; "Also the Huge Pages feature is available" — [highload.fun wiki](https://github.com/Highload-fun/platform/wiki/How-to-use-MMAP-to-optimize-data-reading). A top competitor says the full task statement puts stdin on hugetlbfs — [HN thread](https://news.ycombinator.com/item?id=41044262).
- Judge: Intel Xeon E3-1271 v3 (Haswell) at 3.6 GHz, 512 MB RAM, Ubuntu 20.04, AVX2 only — [Stuchlik, counting bytes](https://blog.mattstuchlik.com/2024/07/21/fastest-memory-read.html).
- Process start and end: with "-static -fno-pie" and `_exit(0)` at the end, a commenter's solution reached about 15,000 points and fourth place (a lower score is a faster run: plain `mmap` builds scored 25,000 to 34,000, the best about 14,700). The thread does not say how much of that came from the linking and the exit alone — [HN thread](https://news.ycombinator.com/item?id=41044262).
- Reading for the prefetcher: Intel's L2 streamer keeps one forward and one backward stream per 4 KB page, up to 32 streams, so the solution reads 8 successive pages interleaved, a cache line from each in turn. About 15% on the score for the counting kernel, up to about 30% for a kernel that is "fully memory bound, single core"; plus `prefetcht0` 4 cache lines ahead in each stream, a distance found by trying ("it's simply what performs best") — [Stuchlik, counting bytes](https://blog.mattstuchlik.com/2024/07/21/fastest-memory-read.html).
- The integer-sum solution reads the input back to front in 32-byte chunks, prefetches 11 cache lines ahead ("chosen empirically"), and indexes a lookup table spanning about 2^42 bytes of address space of which only thousands of 64-byte entries are ever populated — [Stuchlik, summing integers](https://blog.mattstuchlik.com/2024/07/12/summing-integers-fast.html).
- Alexander Monakov's caution, relayed in the thread: "Haswell is tricky for memory bw tuning, as even at fixed core frequency, uncore frequency is not fixed", so an access pattern may win by provoking a higher uncore clock, not by suiting the prefetcher — [HN thread](https://news.ycombinator.com/item?id=41044262).

### Inferences
- `MAP_POPULATE`, static non-PIE linking and `_exit` are in place or measured (`reader-populate`, `fast-exit`, the static image). `MAP_POPULATE` suits a single-threaded judge that counts CPU time; with 8 workers it faults the whole file on one thread under the address-space lock (austindonisan's remark in question 1).
- The page-interleaved read is the one transferable idea, and only for a pass that streams through memory faster than the prefetcher follows on its own. Our event parse is bound by work (our own finding), and the later passes run on 8 threads sharing the memory bus, where a single-core bandwidth trick returns less. If one pass is worth trying it on, it is a pure sequential read of large lists (the place stage reading a partition's list); expect low single digits of that stage, possibly nothing.
- A sparse table in a vast reserved range is what our one up-front reservation already allows.

### Gaps
- No write-up by the first-ranked competitors was found; the top solutions are not public. What is above comes from one competitor's two posts, the platform wiki and a comment thread.
- Nothing found on how highload.fun times a run (wall or CPU, how many runs), nor on output tricks for its tasks; outputs there are a single number.
- Huge pages on the judge: stated as available, no measured gain found.

## 3. Other extreme-throughput programs: input, memory and output handling that could carry over

### Takeaway
The FizzBuzz record and the pipe study behind it are about not copying output into a pipe and about keeping the working buffer inside L2; neither transfers to a program that reads files and writes files, though two of their measurements (huge pages cut the kernel's per-page work, spinning beats sleeping) support choices we have already made.

### Cited Findings
- ais523's FizzBuzz (answer text not retrievable here; code comments as quoted on Hacker News): "the program therefore needs to avoid copies"; `vmsplice` "tells the kernel to place a reference to a buffer into a pipe (as opposed to copying the data into the pipe)"; the target is "a sustained output rate of 64 bytes of FizzBuzz per four clock cycles". Reported by readers: about 55 GiB/s with `taskset`, 38-43 GiB/s without, on the same CPU; 41 GB/s on a 5950X; 7 GiB/s on a Ryzen 1800X — [HN thread](https://news.ycombinator.com/item?id=29031488).
- Mazzoli's reconstruction on a Skylake i7-8550U, Linux 5.17, 256 KiB buffer (the L2 size, as FizzBuzz uses), both ends pinned with `taskset`:

  | Step | Throughput |
  | --- | --- |
  | `write` / `read` | 3.7 GiB/s |
  | `vmsplice` on the writer | 12.7 GiB/s |
  | and `splice` on the reader | 32.8 GiB/s |
  | and 2 MiB pages for the buffer | 51.0 GiB/s |
  | and spinning on `SPLICE_F_NONBLOCK` instead of blocking | 62.5 GiB/s |

  — [mazzo.li](https://mazzo.li/posts/fast-pipes.html)
- Why each step: a plain pipe write is three quarters page copy and page allocation, a page at a time; the huge-page gain ("~50%") is not in the CPU's page walks but in the kernel's own walk to pin user pages (`get_user_pages_fast`), which becomes one lookup and a loop; the last 25% is the wake-up and wait machinery — [mazzo.li](https://mazzo.li/posts/fast-pipes.html).
- FizzBuzz's buffer discipline: one L2-sized block split in two halves, the pipe sized to hold one half, the halves written alternately so the reader has finished one before it is reused; the two buffers allocated separately — [mazzo.li](https://mazzo.li/posts/fast-pipes.html).
- Limits: `vmsplice` "really supports true splicing only from user memory to a pipe"; toward user memory it "actually just copies"; and its safety when pages are spliced onward is "not entirely clear" — [mazzo.li](https://mazzo.li/posts/fast-pipes.html).
- For scale, the same machine's sequential RAM read is about 16 GiB/s (`sysbench`) — [mazzo.li](https://mazzo.li/posts/fast-pipes.html).

### Inferences
- Output: our results go to regular files on a bind mount, where `vmsplice` and `splice` give no zero-copy path from user memory; and the output stage is 8 ms of 230. Nothing to take.
- Input: there is no splice-like call that lends page-cache pages to user space other than `mmap`, so the 8% `pread` copy can only be traded for mapping costs, which we measured as equal.
- The two-half buffer inside L2 is the pipe form of what a worker's reused chunk buffer already is. With two workers on a core, the L2 is shared, so the FizzBuzz rule would put a worker's chunk at half of a thread's share; our sweeps of 256 KB to 1 MB found no difference, so this is confirmation, not a lead.
- The kernel's per-page bookkeeping dominating over bytes moved is the same effect as our unmap of 470,000 4 KB entries; it argues for 2 MB pages wherever the kernel must walk our memory, which the region allocator already gives.

### Gaps
- The primary FizzBuzz answer (Code Golf Stack Exchange) and its web archive copy could not be fetched; buffer and pipe sizes are from Mazzoli's reading of it.
- Fastest `wc` and `yes` write-ups and sortbenchmark single-node entries were not researched in the time available. Sort entries are the nearest public analogue to our large intermediate data (fresh pages, scatter passes) and are the gap most worth a follow-up.

## 4. What the authors report about measurement on noisy machines and with SMT

### Takeaway
The authors who separated small effects fixed the clock, counted per-row hardware events instead of trusting seconds, and learned that anything left running after a process "ends" (a deferred unmap, an orphan) poisons the next run; none describes a method finer than our alternating paired runs.

### Cited Findings
- Clock: Ragnar capped the CPU at 3.6 GHz of a possible 4.6 because it "tends to be more stable for benchmarking", HT off for most tables — [curiouscoding.nl](https://curiouscoding.nl/posts/1brc/). buybackoff: turbo off, fixed 2.5 GHz, `hyperfine --warmup 1 --runs 5`, thermals under 35 °C; AWS metal results that were inconsistent across core counts, "likely from turbo", were excluded — [buybackoff](https://hotforknowledge.com/2024/01/13/1brc-in-dotnet-among-fastest-on-linux-my-optimization-journey/).
- Counters per row: Topolnik steers by instructions per row (2,031 down to 120), branch misses per row and IPC from `perf stat` — [Topolnik](https://questdb.com/blog/billion-row-challenge-step-by-step/). austindonisan reports cycles per row and IPC (14.5 at 2.8), and notes `perf` was unavailable on his cloud instance — [discussion #710](https://github.com/gunnarmorling/1brc/discussions/710).
- Deferred teardown contaminates repeated runs: with the fork trick, `hyperfine` runs slower than manual runs "because the previous `munmap` has not finished" — [discussion #138](https://github.com/gunnarmorling/1brc/discussions/138). charlielye: over 100 runs his no-fork entry averaged 206.8 ± 3.6 ms while a forking entry spread from 181 to 345 ms (219.5 ± 32.0) — [discussion #495](https://github.com/gunnarmorling/1brc/discussions/495).
- CPU binding: `numactl --physcpubind=0-7` made rapid repeated runs 5-10% slower for lehuyduc, 20% at worst; austindonisan went from under 600 ms to about 660 ms with binding over repeated runs (discussion #495 attributes the same 660 ms to the flag that reaps orphans; the two accounts differ) — [discussion #138](https://github.com/gunnarmorling/1brc/discussions/138), [discussion #495](https://github.com/gunnarmorling/1brc/discussions/495).
- Across machines: lehuyduc measures each machine's memory copy bandwidth beside the timings; noahfalk warns the data generators "aren't deterministic", so cross-machine comparisons need "a good amount of fudge factor", and the same Java entries ran 5-10% faster on his CCX33 than on the judge — [discussion #138](https://github.com/gunnarmorling/1brc/discussions/138), [noahfalk README](https://github.com/noahfalk/1brc/blob/main/README.md).
- The judge itself: a cloud VM with dedicated vCPUs was moved to a faster host mid-contest and every earlier result had to be re-run on a dedicated server — [Morling's talk](https://www.infoq.com/presentations/1brc/).
- Multi-socket: page-cache placement makes results depend on the previous run's thread count; flush the cache and pin before changing it — [discussion #138](https://github.com/gunnarmorling/1brc/discussions/138).
- Intel uncore clock is not fixed even at a fixed core frequency — [HN thread](https://news.ycombinator.com/item?id=41044262).

### Inferences
- Our method (alternating variants in one container, 40 runs, quartiles, a second copy on the siblings, instruction counts as the steady signal) is already stricter than any described. What the sources add is a check, not a method: after any change to how memory is released, confirm that back-to-back runs match spaced runs, since a release that outlives the process shows up only in the next run, and the scorer runs three in a row.
- Ragnar's and buybackoff's fixed clocks suggest one cheap extra on the Zen 4 box: a run with boost off, to see whether a 1-2% effect survives when frequency cannot move.

### Gaps
- No author reports a variance model or a statistical test; "separated 1-2%" is not claimed by any of them. Run counts are 5 (1BRC judge, buybackoff, noahfalk), 10-100 (charlielye), 55 (the Go entry).
- Nothing found on measuring under SMT with a deliberately loaded sibling, which is our own harness's method.

## 5. Tricks their authors report as failed or reverted

### Takeaway
The failures cluster in four places: forcing huge pages onto file input, unmapping cleverly from threads, more interleaving than the core can use, and vector gathers on AMD; all four match results we already have.

### Cited Findings
- Huge pages for the input by reading into a `MAP_HUGETLB` mapping: slower than the plain file mapping — [dannyvankooten](https://www.dannyvankooten.com/blog/2024/1brc/).
- A mapping per thread to parallelise the unmap: no gain, the lock is process-wide — [curiouscoding.nl](https://curiouscoding.nl/posts/1brc/). `_exit` to skip the unmap: still paid inside the process's exit — [discussion #138](https://github.com/gunnarmorling/1brc/discussions/138). `MAP_FIXED` overlay in threads: no visible difference in a small test — [discussion #138](https://github.com/gunnarmorling/1brc/discussions/138).
- Hash tables in shared memory between processes: loses 2 MB pages; and waiting for children costs 20 ms — [discussion #710](https://github.com/gunnarmorling/1brc/discussions/710).
- More streams than pay: buybackoff 3-4 against 2, nothing; thomaswue 4 against 3, slower; noahfalk's 4-row vector hash, not worth "loading and unloading the register"; Ragnar's first ad hoc 2-4 way split "didn't work out immediately" — [buybackoff](https://hotforknowledge.com/2024/01/13/1brc-in-dotnet-among-fastest-on-linux-my-optimization-journey/), [Morling's talk](https://www.infoq.com/presentations/1brc/), [noahfalk README](https://github.com/noahfalk/1brc/blob/main/README.md), [curiouscoding.nl](https://curiouscoding.nl/posts/1brc/).
- Gathers on Zen 2 are microcoded and slower than plain loads; emulated PDEP on Zen 1/2 about 3% slower — [discussion #710](https://github.com/gunnarmorling/1brc/discussions/710), [curiouscoding.nl](https://curiouscoding.nl/posts/1brc/).
- A larger table than needed: doubling lehuyduc's hash table added "~0.47ms × N_THREADS" — [discussion #138](https://github.com/gunnarmorling/1brc/discussions/138). noahfalk's first sparse dictionary for 10K keys was "abysmal"; a compact one was about 6x faster — [noahfalk README](https://github.com/noahfalk/1brc/blob/main/README.md).
- Branchless where the branch predicts: branchless min/max rejected by buybackoff (made the loop "backend-bound") and no different for dannyvankooten (the compiler already emits `cmov`); lehuyduc's branchless number parse "1% better in best case" — [buybackoff](https://hotforknowledge.com/2024/01/13/1brc-in-dotnet-among-fastest-on-linux-my-optimization-journey/), [dannyvankooten](https://www.dannyvankooten.com/blog/2024/1brc/), [discussion #138](https://github.com/gunnarmorling/1brc/discussions/138).
- Compiler and flags: `-Ofast` over `-O3` and clang++ over g++ gave nothing or lost for lehuyduc's C++, while GCC lost 15% to Clang on austindonisan's C; `unlikely` hints changed no assembly for Ragnar — [discussion #138](https://github.com/gunnarmorling/1brc/discussions/138), [repo README](https://github.com/austindonisan/1brc), [curiouscoding.nl](https://curiouscoding.nl/posts/1brc/).
- CPU pinning at 8 workers: "slightly harmful" — [1brc.c](https://github.com/austindonisan/1brc/blob/master/1brc.c).
- highload.fun: a smaller lookup table whose index needed a chained `tzcnt` made the index "almost 50% of the runtime"; a table stride of 16 x 64 bytes instead of 11 x 64 was "ultimately much slower" from cache associativity; a non-temporal load "doesn't make a difference" — [Stuchlik, summing integers](https://blog.mattstuchlik.com/2024/07/12/summing-integers-fast.html), [Stuchlik, counting bytes](https://blog.mattstuchlik.com/2024/07/21/fastest-memory-read.html).
- Go: handing chunks to workers through a channel, and copying a chunk before handing it over (which doubled the time) — [r2p.dev](https://r2p.dev/b/2024-03-18-1brc-go/).

### Inferences
- Do not chase: explicit huge pages for input, any thread-side scheme to unmap input faster, a third or fourth cursor, gathers in the decode (already dropped here for the same reason), pinning.
- The doubling-costs-0.47 ms-a-thread figure is an outside measurement of what fresh memory costs at these run lengths, consistent with our 7.5% zeroing: the lever is reserving and touching less, not touching it differently.

### Gaps
- Failures are under-reported: only Ragnar, buybackoff, noahfalk, austindonisan and Stuchlik list them. The Java winners' dead ends are in pull-request threads that were not read.
- No source reports trying and dropping profile-guided or post-link optimisation, so our PGO result has no outside counterpart.
