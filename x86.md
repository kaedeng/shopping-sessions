# M4 vs x86

The scorer is linux/amd64 on an Intel Xeon. Almost every number in `alternatives.md` and `implementation.md` comes from an M4 Pro. On the scorer the submission takes about 1.0 s on about 20M events; the best known time is 0.36 s. Part of that gap comes from costs the Mac does not show. This file covers:

- how the machines differ;
- what we measured on an x86 machine;
- rules of thumb for work done on the Mac;
- how to measure on the x86 machine (Windows, Docker Desktop on WSL2);
- what is not done yet, with what each item is expected to give.

`alternatives.md` holds the options these measurements point to; its rows marked "x86" come from here.

## What we measured on x86

All on the x86 box, 2026-11-21. Release image (HEAD `5c1e1f2`), the scorer's `docker run` flags, and a dataset at the scorer's size read from the Docker volume `ss-p20`:

- `generate --seed 7 --events 20000000 --clicks 5000000`
- 21.58M event lines, 5.08M valid clicks, 0.89M links
- 1.92 GB of CSV

### Whole run

| Measure | Value |
| --- | --- |
| Process, runs back to back | 0.50–0.54 s |
| Process, first run after about 10 s idle | 0.60–0.72 s |
| `docker run` wall on top of the process | about 0.45 s (a container whose entry point fails at once takes 0.40–0.43 s) |
| Scorer against this box | about 1.45× (*estimate*: the scorer's 1.0 s against about 0.69 s here under first-run conditions) |

So 0.36 s on the scorer is about 0.25 s here.

`perf stat`, 3 runs back to back in a privileged container:

- CPU: 3.47 s in all (3.05 s user, 0.36 s system).
- Faults: 33,353 page faults, nearly all of them 2 MB huge pages; no major faults.
- 387 context switches; 5.99 CPUs busy on average.
- Elapsed 0.579 s, against an internal `total` of about 0.54 s.

CPU by function (timer sampling, `perf record -F 1999`):

| Where | Share of samples |
| --- | --- |
| `ingest::parse_with`: tokenizer, per-row parse and partition scatter, all inlined | 51.8% |
| Dedup and person scatter stage | 13.9% |
| Sessions stage | 8.5%, plus `sort_unstable` 6.1% |
| Kernel page zeroing (`clear_page_erms`) | 6.9% |

### Serial gaps between stages

Two runs with `SS_TRACE` (`scripts/trace_summary.py`), in ms:

| | Run 1 | Run 2 |
| --- | --- | --- |
| `parse` lap (`SS_TIMING`) | 291 | 303 |
| Parse tasks, first start to last end | 229 | 242 |
| Serial before the parse tasks | 62 | 61 |
| Serial between the parse and dedup tasks | 40 | 38 |
| Dedup and scatter tasks | 65 | 68 |
| Sessions | 74 | 69 |
| Output | 24 | 21 |

That is about 100 ms of the run with one thread working and seven waiting. The main thread allocates every worker's buffers: 8 × 1,024 partition `Vec`s before the parse and 8 × 2,048 bucket `Vec`s before the dedup stage. glibc writes a header into each chunk. With transparent huge pages, the first write into each 2 MB region faults in and zeroes a whole huge page on that one thread.

Evidence:

- `clear_huge_page`, reached from a libc address, is 6.0% of all samples.
- The parse's own writes fault for only 0.4%.
- `parse_bench` reports 36–42 ms to allocate the parse buffers.

The fix is slot `alloc-parallel` in `alternatives.md`, and its first version taught something the Mac cannot show:

- **Building the same `Vec`s on 8 threads did not help.** The parse's init stage took 63–68 ms on 8 threads against 60–62 ms on one; each worker's build took 8–29 ms, and they took turns.
- **Why.** glibc's per-thread arenas grow with `mprotect`, `mmap` and `munmap`, which take the process's address-space lock (`mmap_lock`) for writing. Every page fault holds it for reading while it zeroes its 2 MB page. Kernel 5.15 has no per-VMA locks (those came in 6.4), so the writers and the faults take turns: `mprotect` averaged 1.37 ms a call on 8 threads against 31 µs on one (`strace -f -c`). glibc's single main arena (`glibc.malloc.arena_max=1`) was no better, since its lock is held through the fault.
- **What worked.** One allocation per worker and record type, the lists carved out of it (`types::parts::Parts`). glibc maps it with one `mmap` and touches only its first page, so the faults happen as the workers write their records, holding the lock only for reading, all at once. The init stages now take 2–3.5 ms; time in those syscalls fell from 0.40 s to 0.10 s; the scorer-like run went from 742 to 597 ms.

### The parse

Like for like (`parse_bench`: fresh mapping, fresh buffers, best of 5):

| Workers | M4 Pro, full size (5.72 GB) | x86 box, 20M (1.92 GB) |
| --- | --- | --- |
| 8 | 17.0 GB/s, 2.13 per worker | 7.2 GB/s, 0.90 per worker |
| 1 | 3.37 GB/s, warm: mapping faulted, buffers reused (not the same conditions) | 1.36 GB/s |

Partition count (`SS_PART_BITS`), `parse_bench` on x86:

| Partitions | 2 | 16 | 64 | 256 | 1,024 (default) |
| --- | --- | --- | --- | --- | --- |
| 1 worker, GB/s | 1.95 | 1.85 | 1.65 | 1.56 | 1.37 |
| 8 workers, GB/s | 11.3 | 10.4 | 8.4 | 7.9 | 7.2 |

On 8 workers the 1,024-way scatter costs about a third of the parse.

- **Instruction level:** 16% of `parse_with`'s samples land right after the store of an `EventRec` into its partition. Another 3% land on the load of that `Vec`'s length and capacity. Timer samples skid one instruction past a stall, so these mark the store and the load.
- **Why x86 only:** per worker, the 1,024 partition tails (64 KB) and the `Vec` headers (24 KB) do not fit a 32 KB L1D. The M4's 128 KB L1D holds them.
- **By source line:** the `flatten` stores of the index pass (`tok.rs:156`) are 8.7% of all samples, about 17% of the parse. The per-row field work is the rest.

The dedup stage shows the same pattern:

- 24.8% of its samples are on the store of a 16-byte `PersonEvent` into one of 1,024 person buckets.
- 9.8% stall right after a prefetch into the link table, presumably with the line fill buffers full.

| Key sort (`sort_unstable`) | 2.02 G | 1.34 | | |

| Kernel | 1.78 G | 0.37 | 1.56 G | 0.32 |

The parse with pieces taken out (temporary builds, 20M, the `parse` lap, which also holds the click rows and the link table):

| | 8 workers | 1 worker |
| --- | --- | --- |
| Whole parse | 235 ms | 1,315 ms |
| Event records parsed but not stored | 165 ms | 1,055 ms |
| Event lines tokenized only, no field parsed | 117 ms | 715 ms |

- **The tokenizer is half the parse.** One core tokenizes 2.7 GB/s here with the fields ignored; the docs give 7.6 GB/s for the M4.
- **Storing the records** costs 260 ms on one core and 70 ms on eight: it scales 4 times, not 8. It is bound by memory traffic: the kernel zeroes every fresh page and the record is then written to it, 1.4 GB in all for the 0.69 GB of partitions. Page zeroing alone tops out near 25 GB/s on this box whatever the thread count (4 GB of 2 MB pages: 13 GB/s on one thread, 24 GB/s on eight).
- **With the scatter staged, the fan-out is nearly free:** 1,024 partitions parse in 213 ms against 194 ms for 2.
- **The mapped input** costs 0.5 µs per 4 KB page to fault in (8 threads, fault-around included) and 0.09 µs to unmap: about 35 ms of worker time per GB.
- **The sessions stage's hottest instruction outside the sort** is the assist counter increment: 36.9M of them at 20M, 10.8 per session.

### Store bypass is disabled in the container

`/proc/self/status` inside every container on this box, started with the default options, with `--security-opt seccomp=unconfined`, with `--privileged` and with the scorer's flags, reads:

```
Speculation_Store_Bypass:       thread force mitigated
```

The VM's own init reads `thread vulnerable` (`docker run --privileged --pid=host debian grep Specul /proc/1/status`), and `/sys/devices/system/cpu/vulnerabilities/spec_store_bypass` reads `Mitigation: Speculative Store Bypass disabled via prctl and seccomp`. An earlier reading in this file said `vulnerable` inside the container; rechecked 2026-11-21.

With the mitigation on, a load does not run until the address of every earlier store is known. A loop whose store address comes out of a load then runs one iteration at a time. A counting scatter is such a loop: the key's position is loaded, the key is stored there, and the next key's loads wait for that store's address.

Measured alone (`rustc -O -C target-cpu=x86-64-v3`, 20,000 session-shaped keys, in a container):

| Loop | Time |
| --- | --- |
| Counting scatter, key by key | 3.5 ns a key per pass |
| The same, eight keys a round: their loads, then their stores | 1.6 ns |
| The same, 16 or 32 a round | slower than 8 |
| `sort_unstable` | 15.9 ns a key (18.5 at 60,000 keys, 24.5 at a million) |
| LSD radix, 8-bit digits, key by key | 30 ns |
| LSD radix, 11-bit digits, eight keys a round | 10.3 ns |

In the run:

- `sort-grouped` with its scatter eight keys a round: the sessions stage is 11% faster than with `sort-std`; key by key it was 7%.
- The radix sort, though faster alone, makes the sessions stage 4% slower than `sort-std`. Not explained.
- The parse and the dedup stage are **not** bound by this. Three changes measured nothing: 128 parsed records buffered before the scatter (parse 235 against 233 ms), the record written field by field into its slot (226 against 223), eight person lookups before any of their stores (dedup 98 against 97).

Whether the scorer runs with the mitigation on is unknown. A kernel before 5.16 turns it on for every seccomp-filtered process unless told otherwise, and Docker's default profile is such a filter; a kernel from 5.16 on does not. A loop written loads-first loses nothing when it is off.

### Other observations

- **CPU quota.** `--cpus 8` on 16 logical CPUs throttled 3 periods over 4 runs, 30 ms in all (cgroup v1 `cpu.stat`). That is about 2% of a run.
- **Memory limit.** `--memory 24g` makes no measurable difference.
- **Speculation mitigations.** Store bypass is disabled for every process in a container here: see "Store bypass is disabled in the container" above. `SpeculationIndirectBranch: conditional force disabled`, with and without `--privileged`.
- **Cold cache.** The first run after an image build read its input cold: `inputs` 281 ms, `total` 1.09 s. `bench_docker.py` does a warm-up round for this reason.
- **Exit.** The process ended about 40 ms after its internal `total` (0.579 s elapsed against about 0.54 s), which also includes process start. It was the kernel unmapping everything on one thread: `free-early` has the workers hand their pages back as they finish with them, and the gap is 3 ms at 20M (5 ms at 60M, where it was 135 ms, and 410 ms with 4 KB pages). Read the process's wall time (`scripts/bench.py`, `wall ms`), not only `total`.
- **Huge-page modes.** With `scatter-wc` and `free-early`, 20M, median total and process wall: `always` 458 and 462 ms, `madvise` 457 and 461, `never` 519 and 543. With 4 KB pages the sessions and output stages lose the most (155 against 109 ms, 28 against 16).

## Rules of thumb for work on the M4

- **Fan-out.** More than about 64 write destinations per thread is cheap on the M4 and expensive on x86. Treat partition and bucket counts as x86 decisions.
  - Schuhknecht, Khanchandani and Dittrich (PVLDB 2015) measured this on a Xeon with a 32 KB L1D. A plain scatter takes 2.41 s to 1,024 partitions and 0.79 s to 32.
  - With one-cache-line software write-combining buffers, streaming stores, and each partition's fill state and destination kept in its buffer line, 1,024 partitions take 0.96 s.
  - Up to about 64 partitions the plain loop is already near the best.
  - Here the same idea (`scatter-wc`) took the parse from 7.7 to 10.5 GB/s. Any new scatter should write through `types::parts::Parts` with `push_as::<M>`, so it gets the staged buffers on x86 and plain stores on the Mac.
- **Allocation.** Never allocate large buffers for every worker on one thread, and do not allocate thousands of small ones on many threads at once either: glibc's heap growth then contends with the page faults for the address-space lock. Give each worker a few large allocations and carve lists out of them (`types::parts::Parts`), built on the worker's own thread (`types::par::init`, slot `alloc-parallel`).
  - With transparent huge pages, each first touch of a 2 MB region zeroes 2 MB on the touching thread. With 4 KB pages it is 512 faults instead.
  - Either way, first touch costs more on x86 Linux than on macOS's 16 KB pages, so count the fresh bytes a change adds.
- **Instruction count.** x86-64 has 16 integer registers, so large inlined row closures spill to the stack. The M4's wide core hides extra instructions and spills.
  - With the scatter nearly gone (2 partitions), one x86 core still parses 1.95 GB/s. The M4's 3.37 GB/s is measured under different conditions, so the comparison is only a hint.
- **SMT.** If the scorer's 8 vCPUs are 4 cores × 2 threads, two workers share each core's L1 and L2, which halves the per-thread cache budget. Unknown.
- **Loads before stores.** In a loop whose store address is computed from a load (a counting scatter, a histogram over loaded keys), take a small batch's loads first and then do its stores: eight at a time measured best. In the container the kernel disables speculative store bypass, and such a loop otherwise runs one iteration at a time ("Store bypass is disabled in the container"). It costs nothing on the M4.
- **Dead memory.** Hand large buffers back when they are dead (`types::mem::release`, slot `free-early`), from the worker that used them. What is still mapped at exit is unmapped by one thread, after the output is written and before the process is gone.
- **Serial work.** At 20M events 10 ms on one thread is 2% of the run. The inputs stage was 14 ms of it.
- **Before deciding.** A change that is neutral on the M4 needs an x86 run before it is decided. Ask Shawn to run `scripts/bench_docker.py` (below), `:base` against the change, for anything that touches:
  - a scatter;
  - allocation or buffer sizes;
  - a record layout;
  - the parse loop.

## Procedure on the x86 box

Windows 10, Docker Desktop on WSL2, commands from Git Bash in the repository root. Python runs as `py -3` (3.12, standard library only).

### Prerequisites

- Docker Desktop.
- Git Bash.
- Python 3: `scripts/bench_docker.py` and `scripts/trace_summary.py` need only the standard library.
- Polars is not needed locally: the correctness checks run in a container.
- `make` works on macOS and Linux only. The Makefile's recipes call `python3` and shell scripts, so on Windows call the scripts below directly.
- Every script sets `MSYS_NO_PATHCONV=1` and hands `docker` Windows paths from `pwd -W`. In a hand-typed `docker` command from Git Bash, do the same, or MSYS rewrites arguments such as `/data`.

### Line endings

`.gitattributes` keeps two kinds of file exact, whatever `core.autocrlf` says:

- `*.sh`, `Dockerfile` and `*.Dockerfile` are always LF.
- `*.csv` and `*.json` are never converted; a `\r` is data under the rules.

Two symptoms show a checkout made with CRLF:

- An image whose entry point fails with `exec /app/run.sh: no such file or directory`.
- 15/36 fixtures passing, with stray `\r` in IDs.

To repair a clone made before `.gitattributes` existed, without changing any content:

```sh
find fixtures dev-answer -type f -exec touch {} +   # make git compare content, not the stat cache
git checkout -- fixtures dev-answer                 # rewrite them with their exact bytes
rm run.sh && git checkout -- run.sh                 # likewise for each scripts/*.sh and Dockerfile
```

### Data

The 20M set the numbers above use:

```sh
(cd generator && cargo build --release)    # a native Windows build; generate.exe takes 2-3 s for 20M
generator/target/release/generate --seed 7 --events 20000000 --clicks 5000000 --output p20
sh scripts/volume_load.sh p20 ss-p20       # empties the volume, then copies the folder into it
```

- `p20/` is in `.gitignore` and `.dockerignore`, so it stays out of commits and out of the image's build context.
- Runs read from the volume, not through a bind mount, which on WSL2 goes through 9p.
- The volume `ss-data` holds `dev/` and the 60M `full/` (5.4 GB), which is tight beside its page cache in the 16 GB Docker VM.

### Images

```sh
docker buildx build --platform linux/amd64 --load -t shopping-sessions:base .     # before the change
docker buildx build --platform linux/amd64 --load -t shopping-sessions:latest .   # after it
```

- Build `:base` before editing, or from a `git worktree` of the base commit.
- A build takes about a minute; there is no dependency-cache layer.
- When a slot has an env var, one image can carry both sides: `shopping-sessions:latest SS_ALLOC=serial` against `shopping-sessions:latest`.

### Correctness

```sh
IMAGE=shopping-sessions:latest sh scripts/check_docker.sh               # expects 36/36 and MATCH
IMAGE=shopping-sessions:latest sh scripts/check_docker.sh SS_PART_BITS=4 NCPU=3
```

The script builds `scripts/check.Dockerfile`: the image's binary plus Polars 2.1.0 and the two check scripts. The first build needs the network for `pip`. It then runs every fixture, and `dev/` against `dev-answer/`. Extra `VAR=value` arguments go to the binary.

### Timing

```sh
py -3 scripts/bench_docker.py -n 6 shopping-sessions:base shopping-sessions:latest
py -3 scripts/bench_docker.py -n 6 --idle 12 shopping-sessions:base shopping-sessions:latest
```

- Each run uses a fresh container with the scorer's flags (`--cpus 8 --memory 24g --read-only`, uid 1000, no network), reads `ss-p20`, and writes its output to a tmpfs.
- The variants take turns, round by round.
- The table shows median (min) per `SS_TIMING` stage, plus `docker run`, and the change against the first variant. `~` means the interquartile ranges overlap.
- Read `total` and the stages. `docker run` includes about 0.45 s of Docker.
- `--idle 12` waits before each run, which gives the scorer-like first-run number (see "Idle reclaim" above). Without it, runs go back to back.
- Use at least 6 rounds and close other heavy programs. Runs vary by about ±10% here.
- Every WSL2 distro shares the Docker VM's CPUs. A job in another distro (the `Ubuntu` one, say) ruins the timings without showing up in `docker ps`: one such job took a run from about 0.6 s to 2 s. Check before timing: `vmmem` in Task Manager should be near idle, or `MSYS_NO_PATHCONV=1 wsl.exe -d Ubuntu -- /usr/bin/top -bn1` should show no busy process.

### Profiling

Build the profile image from the amd64 release image. Rebuild both after a code change.

```sh
docker buildx build --platform linux/amd64 --load --build-arg BASE=shopping-sessions:latest \
  -f scripts/profile.Dockerfile -t shopping-sessions:profile .
PLATFORM=linux/amd64 VOLUME=ss-p20 sh scripts/profile_linux.sh flame      # prof/linux-cpu.svg, .txt
PLATFORM=linux/amd64 VOLUME=ss-p20 sh scripts/profile_linux.sh annotate   # after flame
PLATFORM=linux/amd64 VOLUME=ss-p20 sh scripts/profile_linux.sh syscalls   # strace -c, perf stat
PLATFORM=linux/amd64 VOLUME=ss-p20 sh scripts/profile_linux.sh faults
PLATFORM=linux/amd64 VOLUME=ss-p20 sh scripts/profile_linux.sh trace      # prof/linux-trace.json
py -3 scripts/trace_summary.py prof/linux-trace.json                      # per-stage wall and gaps
```

- **Sampling.** `scripts/profile_linux.sh` samples on a timer. Hardware counters do work in a privileged container on this box (perf 6.12 from Debian trixie's `linux-perf`, 2026-11-21): `perf stat -e cycles,instructions,cache-misses,branch-misses`, and `perf record -e cycles,instructions,branch-misses,L1-dcache-load-misses,ls_any_fills_from_sys.dram_io_all,ls_l1_d_tlb_miss.all,ls_stlf` for a per-function split (`perf list` has the Zen 4 names). The stage tables above come from summing each event's sample periods per symbol out of `perf script -F event,period,ip,sym,dso`.
- **Source lines by hand.** `perf annotate` crashed on this binary with and without `-s`. What worked: `perf script -F ip,sym,symoff,dso --no-inline` for the samples, `nm` for each symbol's address (the binary is position-independent, so a sample's file address is its symbol's plus the offset), then `addr2line -i -f -C -a` for source lines and inline chains and `objdump -d -M intel` for the instructions.
- **One binary, many variants.** `scripts/bench.py` inside one container (`--data /data VARIANT...`, each a command with `VAR=value` words in front) alternates variants without a container start per run and reports the process's wall time, CPU time, faults and peak RSS. Give the container a tmpfs for `TMPDIR`: the VM's 16 GB is too little for stale outputs in the page cache beside the 60M set.
- **Skid.** A sample lands on the instruction after a stall, so read the instruction before a hot one.
- **Source lines.** `perf report --stdio --no-children --sort srcline` maps samples to source lines, but takes a few minutes.
- **Annotate.** `perf annotate -s <symbol>` crashed here; the unfiltered `perf annotate --stdio` worked.
- **Serial gaps.** The trace has no span for serial work. The gap before the first stage is the `parse` lap from `SS_TIMING` minus the parse stage's wall in the summary.
- **Throttling.** To see quota throttling, read `/sys/fs/cgroup/cpu/cpu.stat` (cgroup v1 under WSL2) inside a container after a run.

### One stage alone

A crate's bench runs in the Rust build image, with its target directory and Cargo registry kept in volumes. For example, the parse with fresh mapping and buffers:

```sh
export MSYS_NO_PATHCONV=1
docker run --rm -v "$(pwd -W)":/src:ro -v ss-target:/target -v ss-cargo:/usr/local/cargo/registry \
  -v ss-p20:/data:ro -e CARGO_TARGET_DIR=/target -w /src rust:1.98-slim-trixie sh -c '
    cargo build --release -p ingest --example parse_bench --locked &&
    export GLIBC_TUNABLES=glibc.malloc.hugetlb=1:glibc.malloc.top_pad=268435456:glibc.malloc.mmap_threshold=33554432 &&
    NCPU=8 /target/release/examples/parse_bench /data'
```

`SS_PART_BITS`, `SS_TOK` and `NCPU` apply as in the binary.

### What this machine cannot do

- **Store bypass allowed.** Every container has the mitigation on, so a run with it off cannot be timed here ("Store bypass is disabled in the container").
- **Scorer-like idle.** Runs after idle carry the WSL2 memory-reclaim cost described above.
- **SMT.** With 16 logical CPUs for 8 workers, a worker usually has a core to itself. If the scorer's vCPUs are hyperthreads, this box understates the cache pressure.

### `links-first`: the design that was worked out

- **No concurrent union-find is needed.** The parse writes each event as today's 32-byte record into a small pending list. When the list is full and the link table is ready, it is flushed: the person is looked up, the `PersonEvent` goes to its person bucket and a 16-byte `{event_id, ingest, location}` to its dedup partition. Until the table is ready the pending list just grows (about 36 MB per worker over the 50 ms the build takes at 20M), and the click chunks never need the table at all.
- **The location** of a `PersonEvent` is its bucket and its index in the worker's list for that bucket, in 32 bits; the worker is known from which piece the dedup record came from. An index too large for its bits goes through a per-worker side list of `(bucket, index)` pairs, so no input is rejected.
- **The dedup task** keeps, per `event_id`, the copy with the smallest `ingest`, and marks every other copy's `PersonEvent` dead (`person = 0`, the empty ID) through its location. Two tasks never mark the same record. A winner that is invalid has no `PersonEvent`, so nothing survives, as the rules ask (fixtures E4 and E5 are the cases to keep passing).
- **The sessions stage** skips dead events as it gathers.
